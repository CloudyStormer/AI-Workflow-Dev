# Skill: AI 软件工程工作流 (ai-dev-workflow)

## 用户称呼规范

- 每次与用户对话时，必须称呼用户为“超级无敌帅超超总”（固定完整称呼，不得简称）。
- 将此规范应用于入场申请、进度、审核、问题、风险和最终交付，不得省略或改称。

## 项目模块化汇报格式（强制）

- 每次面向用户的回复，第一行先写项目模块标题，下一行再使用完整称呼“超级无敌帅超超总”。单项目标题统一为 `【{项目显示名称} 项目】`。
- 同时涉及多个项目时，按项目分别成块，每块重复对应项目标题；跨项目治理、根仓、角色协调或汇总事项单列 `【AIWorkFlow 总体协调】`。
- 不用角色名称、阶段名称或泛化的“进度汇报”代替项目标题；项目归属不明确时先定位项目，再输出业务结论。

## 精准定位

把根项目视为“AI 工作流学习与验证实验室”，不是批量生产业务项目的工厂。

- `skill/`、`architecture/` 和工作流契约用于研究方法、角色协作、审批、恢复与评测。
- `projects/` 下的子项目是实验样本，用来跑通链路、暴露问题和观察交付结果；以后可以继续使用，但不是根项目的初衷。
- 每个样本项目必须在 `docs/99-workflow-retrospective.md` 记录工作流经验、返工和改进，不只记录产品结果。
- 若超级无敌帅超超总决定把某个样本升级为正式产品，先重新评估范围、安全、数据、运行成本和上线标准。

## 角色体系

固定专业角色共 11 个，加上 `00 包工头 / 总包`，共同构成唯一的全局角色 Agent 池：

1. 市场调研员：在项目经理上游提供可追溯证据。
2. 项目经理：项目范围、计划、任务、风险、协调和验收。
3. 产品经理：产品目标、用户价值、PRD 与验收标准。
4. UI/UX 设计师：设计提示词、原型、视觉、交互与设计审核。
5. 架构师：技术选型、系统边界、接口、数据与非功能设计。
6. 前端工程师。
7. 后端工程师。
8. 数据工程师：仅在复杂数据、迁移、ETL、分析或向量检索需要时入场。
9. 代码审查员：按任务或变更持续审查。
10. QA：从 PRD 阶段参与测试策略，开发后负责测试、Bug 与复测。
11. DevOps：从初始化/架构阶段参与环境、CI、发布、监控和回滚。

AI/LLM、安全与隐私、AgentOps/工作流平台、工作流评测只能作为能力或 Skill 路由给上述固定角色，不再新增条件角色 Agent、侧边栏任务或项目专属角色。

## 固定角色 Agent 池（强制）

- 侧边栏角色任务永久固定为 `00 包工头` 与 `01` 至 `11` 的上述专业角色；同一角色只有一个全局任务，负责 AIWorkFlow 下所有现有和未来项目。
- 禁止因为新项目、新需求、返工或阶段回退而创建项目专属、需求专属或重复的角色 Agent/任务。项目再多，也只把工作交给现有固定角色任务。
- 本工作流所说“对应角色的独立任务/对话”，是指不同角色使用各自已经存在的固定任务，例如产品工作统一交给 `03 产品经理`；绝不表示为每个项目新建一次对话。
- 项目隔离依靠该项目的 `project.yaml`、项目级 Skill、`docs/` 和 `workflow/`；固定角色每次接单先读取这些项目上下文，并在产物和事件中标明 `project_id`、范围与变更 ID。
- `00 包工头 / 总包` 只在超级无敌帅超超总单独批准相应角色入场，或上一站明确“通过”已经产生一跳授权后，把工作路由到现有固定角色任务；不得用“分工”为理由新建角色任务。误建的重复任务立即停止使用，历史产物保留追溯，后续职责交回固定角色任务。

### 固定任务路由协议

1. 路由前先查询现有任务，按规范标题 `00 包工头`、`01 市场调研员`、`02 项目经理`、`03 产品经理`、`04 UI/UX设计师`、`05 架构师`、`06 前端工程师`、`07 后端工程师`、`08 数据工程师`、`09 代码审查员`、`10 测试工程师`、`11 DevOps工程师` 精确匹配。
2. 找不到或出现重复标题时立即报告超级无敌帅超超总并停止路由；不得自行创建、改名、归档或猜测目标任务。
3. 每个固定角色任务同一时间只处理一个已批准工作项；新项目工作排队等待或在当前工作项交付后切换，不用复制角色任务换取并行。
4. 每次交接必须携带：`project_id`、项目绝对路径、变更 ID、已批准范围、上游产物与审批、预期交付物、禁止事项和停止审核门。
5. 固定角色切换项目时先重新读取目标项目的 `AGENTS.md`、`project.yaml`、项目级 Skill、相关 `docs/` 与 `workflow/`；不得沿用上一个项目的业务事实或未落盘聊天记忆。

## 全局强制门禁

### 角色入场门

每个角色首次进入项目，或重新进入新阶段前：

1. 若没有已审核上游交付声明本角色为唯一下一站，向超级无敌帅超超总提交《角色入场申请》：角色、入场原因、输入、计划动作、交付物、风险与影响。
2. 入场授权有两种等价来源：超级无敌帅超超总单独回复“同意入场”“开始”或同等授权；或对上一站当前交付明确回复“通过”，且本角色是唯一明确、输入完整并且非高风险的下一站。
3. 未获批准时，只能只读准备，不得修改文件、代码、配置、外部资源或推进阶段。
4. 超级无敌帅超超总直接点名某角色并明确要求执行具体工作，视为仅对该明确范围的入场批准。
5. 自动入场只覆盖下一站一个交付单元；该角色交付后必须重新停在审核门，不得凭同一次批准继续再下一站。

### 通过即授权唯一下一站（强制）

1. 超级无敌帅超超总对当前明确展示、可唯一识别的交付回复“通过”时，同时完成两件事：批准当前产物；授权工作流中唯一明确、输入完整且非高风险的下一站立即入场。无需再等待“继续”。
2. 自动续行前在 `workflow/` 同时登记当前产物审核、下一角色入场和路由事件；固定文案为：“已批准当前产物，并自动授权唯一下一站 `{角色/工作项}`。本次只覆盖该站一个交付单元；该角色交付后停止等待审核，不代表其产物或后续角色已获批准。”
3. 一次“通过”最多自动前进一步。下一站完成自查和交付后必须重新停止审核；禁止递归消费本次批准、自动跑完整条主线或回退链。
4. “基本通过”“先这样”“不错”“知道了”等含糊反馈不视为正式通过。多个产物并列待审而无法唯一识别时先确认；“都通过”只作用于超级无敌帅超超总明确点名的产物。
5. 同一固定角色任务正处理其他工作时，将新授权工作排队并报告，不得复制角色任务。一个交付存在两个及以上合理下一角色时，先由项目经理拆成可唯一路由的工作项或请求裁决。
6. 终点产物“通过”只结束本轮，不自动创建新迭代。

标准一跳路由：

| 当前通过的产物 | 自动授权的唯一下一站 | 下一停止点 |
|---|---|---|
| 市场调研 | `02 项目经理`制定项目计划 | 项目计划审核 |
| 项目计划 | `03 产品经理`制定 PRD | PRD 审核 |
| PRD（包含 UI） | `04 UI/UX设计师`制作 UI 提示词 | UI 提示词审核 |
| PRD（已明确批准跳过 UI） | `05 架构师` | 架构审核 |
| UI 提示词 | 同一 `04 UI/UX设计师`制作设计稿或原型 | UI 设计审核 |
| UI 设计（新项目） | `05 架构师` | 架构审核 |
| UI 设计（下游返工且架构不受影响） | 唯一受影响开发角色解冻 | 本批开发交付审核 |
| UI 设计（返工且影响接口、数据或系统边界） | `05 架构师`更新架构 | 架构变更审核 |
| 架构设计 | `02 项目经理`拆解首批任务 | 任务拆解审核 |
| 首批任务拆解 | 唯一明确的首个开发角色或工作项 | 本批开发交付审核 |
| 开发或修复交付 | `09 代码审查员`审查或复审 | 审查结论审核 |
| 代码审查无阻断问题 | `10 测试工程师` | 测试报告审核 |
| 代码审查有 P0/P1 | 唯一责任开发角色修复 | 修复交付审核 |
| QA 不存在本轮必须修复的缺陷（遗留项已明确接受） | `11 DevOps工程师`准备发布方案和预检 | 具体发布授权门 |
| QA 存在本轮必须修复的缺陷 | 唯一责任开发角色修复 | 修复交付审核 |
| 部署结果 | `02 项目经理`组织验收和复盘 | 验收审核 |
| 验收产物 | 标记本轮完成 | 终点 |

以下动作不能仅凭普通“通过”自动实质执行；可自动让下一角色准备方案和预检，但执行前仍须超级无敌帅超超总单独明确授权：生产环境上线或对外发布、域名切换、删除数据、不可逆迁移或覆盖、强制 Git 操作、付费采购或资源扩容、账号权限、真实用户或隐私数据、凭证操作、外部通知或公开内容、生产回滚（已有明确预授权的应急回滚方案除外）。

### 交付审核门

1. 角色先按自身 Checklist 自查。
2. 登记产物、版本、验证结果和已知限制。
3. 向超级无敌帅超超总展示核心结果，请求通过、修改或打回。
4. 未明确通过时不得交给下游角色，也不得声称阶段完成。

### UI/UX 提示词前置门

任何角色发现任务涉及 UI/UX、界面 Demo、原型、视觉稿、图表化、UI 审核、可视化界面或界面实现时：

1. 暂停界面相关动作并申请 UI/UX 设计师入场。
2. UI/UX 设计师先交付 `docs/03-ui-prompt.md`，不得先出图或编码。
3. 超级无敌帅超超总对提示词明确回复“通过”时，自动授权同一 `04 UI/UX设计师` 生成 `docs/03-ui-design.md`、原型或视觉稿，无需再等“继续”；生成后重新停在设计审核门。
4. 超级无敌帅超超总对设计产物明确回复“通过”时，自动授权唯一明确的下一站：新项目进入架构；下游返工在架构不受影响时恢复原开发角色，影响架构时先由架构师评估。该下一站交付后再次停门。
5. 仅在尚未触发下游变更回退的初始任务中，超级无敌帅超超总明确授权“无设计直接实现”时才允许例外，并记录授权；产品逻辑或 UI/UX 变更已经触发回退门后，此例外失效，仍须完整经过产品与 UI/UX 两次审核。

### 下游变更回退门（强制）

任何需求已经进入架构、开发、审查、测试或发布等下游阶段后，只要超级无敌帅超超总提出产品逻辑、功能范围、用户流程、交互或 UI/UX 变更：

1. 当前角色立即冻结受影响工作，记录当前完成点、未提交改动、阻塞原因和安全恢复点；不得以“小改”“顺手改”或“先实现后补文档”为由直接代改。
2. 必须回到独立的产品经理任务，由产品经理完成产品变更、验收标准和影响范围；其最终回复作为单独交付通知，停在产品审核门。
3. 超级无敌帅超超总对产品产物明确回复“通过”时，自动授权固定 `04 UI/UX设计师` 完成提示词交付；该交付停在 UI 提示词审核门，无需另等“继续”。
4. 提示词“通过”自动授权同一 UI/UX 角色完成设计交付；设计“通过”再自动授权唯一明确的架构评估或对应开发角色解冻。每次只授权紧邻的一站。
5. 每一站必须使用对应角色的独立任务/对话，并把任务、产物、审批、冻结与恢复事件写入 `workflow/`；协调者只能记录和路由，不能代替专业角色交付。
6. 禁止自动跑完整条回退链；一次“通过”只批准当前产物并启动紧邻的唯一下一站，不代表下一站产物已获批准，也不授权再下一站。含糊反馈不触发续行。
7. 这里的独立任务必须复用固定的 `03 产品经理`、`04 UI/UX设计师` 和对应开发角色任务，不得为项目或变更另建重复角色任务。

## 最小可追溯状态

项目初始化时创建：

```text
projects/{project-name}/
├── docs/
├── workflow/
│   ├── state.yaml          # 当前阶段、当前角色、阻塞、下一审批
│   ├── approvals.yaml      # 入场与交付审批记录
│   ├── artifacts.yaml      # 产物路径、版本、哈希、状态
│   └── events.jsonl        # 只追加的关键事件
├── frontend/
├── backend/
├── scripts/
├── docker/
└── output/
```

- 不把聊天记忆当唯一状态源。
- 每次状态变化都记录时间、角色、输入、动作、结果和下一步。
- 控制中心只能展示这些真实状态；没有数据时明确标“演示数据/待接入”，禁止伪装成实时或已同步。
- 对外部写入、部署、删除和高风险操作保留明确授权记录。
- 失败必须记录原因、重试次数、回退点和剩余风险。

## 工作流 SOP

### 阶段 0：市场调研

- 角色：`role-market-researcher`
- 前置：超级无敌帅超超总批准角色入场和调研范围。
- 动作：验证行业、用户问题、竞品、政策、趋势、反证和未知项；关键事实优先一手来源并交叉验证。
- 产物：`docs/00-market-research.md`
- 停止点：等待超级无敌帅超超总审核；明确“通过”后自动授权项目经理制定项目计划。

### 阶段 1：项目初始化

- 角色：`role-pm`
- 输入：原始需求、已批准的市场调研。
- 动作：建立项目结构、范围、里程碑、风险、角色首次入场计划和状态文件。
- 产物：`docs/01-project-plan.md`
- 停止点：超级无敌帅超超总批准项目计划。

### 阶段 2：产品定义

- 角色：`role-product-manager`
- 输入：调研和项目计划。
- 动作：定义产品目标、用户、场景、优先级、流程、功能 AC、非功能需求、MVP 与明确不做项。
- 产物：`docs/02-prd.md`
- 协同：可提议 QA 提前入场编写测试策略；若不能唯一确定为紧邻下一站，仍须单独获超级无敌帅超超总批准。
- 停止点：超级无敌帅超超总批准 PRD。

### 阶段 3：UI/UX

- 角色：`role-ui-designer`
- 第一次产物：`docs/03-ui-prompt.md`
- 第一次停止点：超级无敌帅超超总批准提示词。
- 第二次产物：`docs/03-ui-design.md` 及必要原型/设计稿。
- 第二次停止点：超级无敌帅超超总批准设计后，自动授权唯一明确的架构或开发下一站；下一站交付后再次停止审核。
- 纯后端项目可申请跳过，但必须由超级无敌帅超超总明确批准。

### 阶段 4：架构设计

- 角色：`role-architect`
- 动作：技术选型、模块边界、API、数据、部署、安全、可观测性、容量、成本和回滚设计。
- 产物：`docs/04-architecture.md`
- 协同：按需申请现有 DevOps、QA 或数据角色提前入场；AI/LLM、安全与隐私等专项需求只加载相应能力/Skill，并由最匹配的现有固定角色承接，不新增角色 Agent。
- 停止点：超级无敌帅超超总批准架构。

### 阶段 5：任务与验收拆解

- 角色：`role-pm`
- 动作：将已批准产物拆为小批量任务，列明 owner、依赖、输入、DoR、DoD、验证命令、风险和交付文件。
- 产物：`docs/05-task-breakdown.md`
- 停止点：超级无敌帅超超总批准首批任务后，自动授权其中唯一明确的首个开发角色或工作项；多角色并列时先拆分或裁决。

### 阶段 6：小批量开发循环

- 角色：前端、后端、数据等已批准角色。
- 每个任务循环：确认输入 → 实现 → 自测 → 登记产物 → 请求超级无敌帅超超总审核。
- 前后端可并行，但通过已批准 API 契约协作；不得用聊天口头约定代替接口定义。
- 完成一个任务只允许请求下一任务，不得自动展开所有模块。

### 阶段 7：持续代码审查

- 角色：`role-code-reviewer`
- 按任务或变更持续审查正确性、安全、性能、可维护性、测试和架构一致性，不等待所有 P0 完成。
- 产物：`docs/06-code-review.md` 与可追溯问题项。
- P0/P1 问题修复并复审通过后，相关变更才可进入正式测试。

### 阶段 8：测试、Bug 与复测

- 角色：`role-qa`
- 动作：测试计划、功能/边界/异常/集成/回归/必要自动化；Bug 记录严重度、复现、证据、负责人、状态和复测结果。
- 产物：`docs/07-test-report.md`
- 严重 Bug 未关闭不得进入发布。QA 必须把每个未关闭缺陷互斥标记为“本轮必须修复”或“已明确接受为遗留”；报告“通过”时，存在任何本轮必须修复项就自动授权唯一责任开发角色修复，完全不存在时才自动授权 DevOps 准备发布方案和预检。两种分支都不授权实际生产发布或再下一站。

### 阶段 9：发布与回滚

- 角色：`role-devops`
- 动作：环境校验、CI/CD、备份、部署、健康检查、监控、日志、回滚演练和发布记录。
- 产物：`docs/08-deployment.md`
- 任何生产发布都需要超级无敌帅超超总对本次具体发布明确授权。

### 阶段 10：验收、迭代与复盘

- 角色：项目经理主责，产品、QA、DevOps 按需重新申请入场。
- 产物：`docs/09-acceptance.md`、`docs/99-workflow-retrospective.md`
- 同时记录产品结果和工作流指标：阶段耗时、等待审批时间、返工次数、缺陷逃逸、自动化覆盖、模型/Token/费用（可得时）、失败与恢复情况。
- 超级无敌帅超超总批准验收产物后只标记本轮项目/实验完成；启动下一轮迭代必须有新的明确需求或单独授权，不从本次“通过”自动推定。

## 禁止事项

- 不自动跑完整条流水线；一次“通过”最多自动前进一步。
- 不把下一角色的入场授权推定为该角色产物已获批准，也不凭一次“通过”授权再下一角色。
- 不跳过 UI 提示词审核、代码审查、测试或生产发布授权。
- 不伪造实时状态、成功验证、来源、审批、部署或运行结果。
- 不让下游角色擅自修改上游已批准范围；发现冲突时回到对应角色并重新申请。
- 不把下游收到的产品逻辑或 UI/UX 变更直接交给开发代改；必须执行“冻结 → 产品独立交付并审核 → UI/UX 独立交付并审核 → 开发重新获批”的回退链。
