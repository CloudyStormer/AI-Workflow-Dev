## 1. 项目目标与立项判断

### 1.1 产品目标

在不依赖违规抓取或受限社区平台的前提下，验证一个面向超级无敌帅超超总的“大模型动态聚合”工具是否能够：

1. 以官方主源为优先入口，汇集国内外重要模型、API、开源、研究、评测、安全、服务状态和监管动态。
2. 把同一事件的多条传播内容聚合为可追溯事件，保留主源、佐证、反证、时间和版本信息。
3. 每日最多筛选 10–20 条高价值事件；高置信事件不足时明确说明，不为填满配额而降质。
4. 区分已确认事实、来源观点、系统推断和待核验线索，并展示置信度与原文链接。
5. 用 14–30 天影子运行取得真实候选量、独立事件量、重复率、相关性、漏报和核验成本，为继续自建、购买现有服务或调整范围提供证据。

### 1.2 AI 工作流实验目标

本项目同时是 AIWorkFlow 的第二条实验样本，重点观察：

- 固定角色任务能否在不创建项目专属角色的情况下保持项目隔离。
- 市场调研证据能否无失真地进入项目计划、PRD、架构、开发和验收。
- 角色入场门、交付审核门和下游变更回退门能否阻止越权推进。
- 产物、审批、SHA 和事件能否构成可恢复、可复核的最小状态链。
- 返工、等待审批、失败恢复、人工修改和模型/Token/费用（可得时）能否被如实记录。

### 1.3 当前立项判断

结论为“**有条件继续验证，不承诺已经具备可运行产品或商业可行性**”。官方新闻、changelog、RSS/JSON、GitHub、论文、评测与监管源足以支持第一版验证；但每日高价值事件产量、去重效果、用户偏好、真实节省时间和长期成本尚无连续运行证据，必须通过影子运行补证。

## 2. 范围与 MVP 规划边界

以下是项目计划层面的 MVP 范围包络，最终功能、流程和定量阈值必须由后续获批的产品经理写入 PRD，再经超级无敌帅超超总审核。

### 2.1 MVP 范围内

| 范围 | 计划级边界 |
|---|---|
| 来源注册与停用 | 记录来源身份、访问方式、自然频率、robots/条款核验时间、保留边界、责任人和源级停用开关。 |
| 合规采集 | 先验证市场调研定义的 A–D 级来源：官方 RSS/Atom/JSON/API、允许低频访问的公开 changelog、白名单 GitHub Release、论文与独立评测。 |
| 最小数据 | 只保留规范化链接、标题、发布方、发布时间、取得时间、事件字段、短自写摘要、证据类型、置信度和必要指纹。 |
| 事件聚合 | 支持 URL、精确内容、实体/版本/动作和跨语言候选的分层去重；跨语言语义只能给出候选，不能脱离规则直接合并。 |
| 证据与标签 | 每个正式事件保留主源；区分事实、来源观点、系统推断、待核验，并可关联技术佐证、独立佐证和反证。 |
| 筛选与输出 | 形成每日最多 10–20 条的高置信事件摘要；不足时宁缺毋滥；支持后续 PRD 定义的定时刷新和按需刷新。 |
| 紧急信号 | 只把官方状态、安全公告、明确下线/价格生效或监管紧急通知作为 P0 候选，不把全网分钟级监测作为默认目标。 |
| 影子运行 | 连续 14–30 天运行并进行人工复核，形成产品质量、来源贡献、运营成本和买/建比较证据。 |

### 2.2 非目标

- 不做全网爬虫，也不以抓取站点数、文章数或必须凑满 10–20 条作为成功标准。
- 不把 X、Reddit、微博、哔哩哔哩等受 robots、API、版权、登录或开发者准入约束的社区来源设为 MVP 刚性依赖。
- 不使用浏览器 Cookie、共享账号、模拟登录、绕过访问控制、反爬或付费墙的方式获取内容。
- 不默认保存或再分发全文、图片、视频、完整字幕、评论、付费 Newsletter 或个人资料。
- 不在本计划中确定 PRD、页面流程、视觉方案、技术栈、接口、数据库、部署方式、预算或生产容量。
- 不承诺分钟级全量实时、公开商用、多用户平台、自动发布或生产上线。
- 不自动采购付费 API、Newsletter 或第三方聚合服务；任何采购和账号申请需单独批准。
- 不把厂商“领先/SOTA/第一”等自述改写为客观事实，也不把社区热度直接当作重要性。

## 3. 核心交付物与验收口径

### 3.1 当前项目计划交付验收

本计划 v1.0 通过需同时满足：

- 目标、MVP 包络、非目标、里程碑、依赖、风险、合规约束、角色入场计划和验收口径完整。
- 所有产品边界均能追溯至已批准的市场调研，没有把受限社区源升级为刚性依赖。
- 明确当前无代码、无真实入口、不可运行，不伪造测试、部署、成本或用户规模。
- 每个交付仍需独立审核；对当前交付回复“通过”时，只同时授权唯一、明确的下一站继续。本计划的唯一下一站是固定 `03 产品经理`，因此“通过项目计划”同时构成其本轮产品定义入场授权；不会继续授权 UI/UX、架构或任何更后阶段。
- `workflow/` 登记计划路径、版本、SHA、状态和交付事件，且只修改本项目范围文件。

### 3.2 后续 MVP 候选验收框架

最终定量阈值必须在 PRD 和测试策略中批准；在阈值批准前，以下为不可删除的最低验收维度：

1. **来源合规：** 100% 已启用来源具有访问模式和条款/robots 核验记录；受限来源未经单独批准的启用数量为 0。
2. **可追溯性：** 100% 正式事件具有可直接打开的主源链接、发布方、事件时间、取得时间、证据标签和置信度。
3. **内容最小化：** 未经批准保存的全文、媒体、完整评论、付费内容或登录态数量为 0。
4. **质量测量：** 必须报告来源成功率、候选量、独立事件量、近重复率/聚类压缩率、人工相关性、漏报、平均核验时间和人工改分率。
5. **去重验证：** 使用人工标注的同事件/非同事件样本报告 precision/recall；阈值由 PRD/测试策略基于影子基线审批。
6. **产量诚实：** 每日正式摘要不超过 20 条；不足 10 条时明确标记高置信事件不足，不以低质量内容补位。
7. **事实安全：** 厂商声明、独立验证、系统推断和待核验线索不能混写；高影响推断必须能回看依据。
8. **运行证据：** 至少完成连续 14 天影子运行；若样本不足以做决策，可在批准后延长至 30 天，不伪造“稳定日更”结论。
9. **决策产物：** 影子运行结束后形成继续自建、缩减/扩大范围、采购组合替代或停止项目的证据化建议。
10. **工作流治理：** 角色入场、交付审核、产物 SHA、关键事件记录完整；未授权跨阶段推进和跨项目文件污染均为 0。

## 7. 合规与内容安全约束

1. **官方源优先：** 正式事件必须回到主源；社区、媒体、Newsletter 和聚合站只作发现或独立解读，不能以转载数量冒充独立证据。
2. **访问双重校验：** robots 是爬虫访问规则，不是授权；实现前需同时核验 robots、服务条款、API 条款、速率限制和所需资格。
3. **受限来源默认关闭：** X、Reddit、微博、哔哩哔哩及任何需登录、Cookie、付费、开发者申请或商业协议的来源，未经单独批准不得自动接入。
4. **禁止规避：** 不模拟登录、不共享凭证、不绕过反爬/付费墙/访问控制、不利用浏览器登录态替代正式授权。
5. **数据最小化：** 默认不保存全文、图片、视频、完整字幕、评论或个人资料；使用自写短摘要、最小元数据和原文回链。
6. **版权与再分发：** 不复制 Newsletter/媒体正文，不热链受限媒体，不去除水印；必要引用保持最短并标明出处。
7. **删除与停用：** 来源条款变化、访问异常或删除要求触发源级停用；需要删除同步的平台必须在启用前设计相应机制。
8. **生成内容标识：** 若未来向中国境内公众提供模型生成摘要，产品、合规和架构阶段必须复核适用的生成合成内容标识、服务治理和备案要求。本计划不是法律意见。
9. **事实表达：** 厂商自述必须写成“厂商称”；系统推断展示依据和置信度；冲突证据与反证不得隐藏。
10. **凭证安全：** API Key、访问令牌、Cookie、账号、`.env` 和其他秘密不得进入 Git、事件或产物正文。

## 9. 关键决策点

1. **计划通过决策：** 同时批准本项目计划，并授权唯一、明确的下一站固定 `03 产品经理` 进入本轮产品定义；不授权 UI/UX、架构或更后阶段。
2. **PRD 决策：** 明确最终 MVP、偏好、质量阈值、定时/按需刷新边界以及是否需要紧急提醒。
3. **来源准入决策：** 影子运行若证明社区或付费源存在不可替代缺口，再逐源决定 API 申请、采购、授权或保持关闭。
4. **买/建决策：** 用免费核心池影子数据对照 Feedly、AlphaSignal、Newsletter/RSS 组合的覆盖、质量、成本和维护量；没有证据前不默认自建必胜。
5. **范围决策：** 若 30 天平均每日不足 6 个独立高分事件且仍要求 10–20 条，必须选择降低数量目标、扩大到 AI 基础设施/应用/产业，或停止；不得静默改变定位。
6. **公开/商用决策：** 从个人内部工具扩大到公开或商业服务前，重新评估版权、隐私、标识、备案、安全、成本和服务标准。
7. **生产发布决策：** 任何生产发布均需针对具体版本、环境和回滚方案单独授权。

## 11. 变更、沟通与停止规则

- 范围、MVP、用户流程、内容标签或 UI/UX 的变化必须回到对应角色产物并重新审核，不能由开发“顺手修改”。
- 一旦进入架构、开发、审查、测试或发布，下游收到产品逻辑或 UI/UX 变更，立即冻结受影响工作，依次经过固定 `03 产品经理`、固定 `04 UI/UX设计师` 和对应开发角色重新获批。
- 每个阶段交付后，当前角色先自查、登记产物与 SHA、单独通知超级无敌帅超超总并停止。超级无敌帅超超总回复“通过”时，同时授权唯一、明确的下一站继续；下一站完成后必须再次独立交付和停止，不能继承到更后阶段。下一站不唯一、范围有歧义，或涉及生产发布、删除、付费时必须单独请示。
- 风险升级条件包括：敏感数据或凭证暴露、来源条款冲突、版权投诉、高影响错误摘要、跨项目文件污染、验证失败、Git 冲突或无法安全恢复。发生时冻结相关范围，保留现场并报告。
