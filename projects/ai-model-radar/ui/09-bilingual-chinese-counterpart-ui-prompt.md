## START OF DESIGN PROMPT

你是一名资深中文新闻产品与数据产品 UI/UX 设计师。请为 **AI Model Radar（AI 开发圈新闻雷达）** 设计“逐条中文对照”增量：在不改变原文事实根、不隐藏一手证据的前提下，为每条正式新闻事件提供清楚、可信、可追溯的简体中文对照。

目标体验是：

**中文用户先读懂事件 → 随时核对原文 → 看清中文内容如何形成、是否最新 → 在详情和历史中追踪原文与中文版本的对应关系。**

界面必须极简、干净、信息层级明确；减少解释性大段文字，以并列内容、短标签、版本关系、状态条和结构化字段表达事实。全部导航、操作、状态反馈、筛选、错误和无障碍文案使用完整简体中文；专有名词和不可翻译字段按本 Prompt 原样保留。

### 一、不可妥协的事实与设计原则

1. **原文是事实根。** 中文内容是附加对照，不替代、不覆盖、不改写原始标题、原始摘要、原始证据、来源和时间。
2. **每条都有明确结果。** 正式事件必须显示中文内容，或明确显示“译文生成中”“译文待更新”“译文生成失败”“暂无译文”，不得留出含义不明的空白。
3. **形成方式可见。** 使用互斥标签“人工译文”“机器翻译”“规则生成”“无译文”；不要用模糊的“AI 优化”“智能摘要”。
4. **形成方式不等于事实层级。** “人工译文/机器翻译/规则生成/无译文”描述中文内容如何形成；“来源事实/来源观点/系统摘要/系统评估/待确认”描述内容性质。两组标签必须分区呈现，不能混为一个颜色体系。
5. **专有内容保真。** 发布方、模型、产品、仓库、API、SDK、Agent、框架、版本号、tag、commit、CVE、许可证、模型 ID、端点、文件名、命令、配置键、错误码、URL、路径、日期、时间、价格、单位、百分比、上下文窗口原样保留。
6. **不确定时保留原文。** 不确定术语不得强行意译；保留原词，并以“译法待确认”就近标注。
7. **不扩写事实。** 不把营销话术改成事实，不把观点改成事实，不把 commit/update 改成正式发布，不虚构性能、对比、结论或开发者行动。
8. **失败不影响新闻。** 中文处理失败、超时或局部不可用时，真实新闻、原文、证据链和已发布快照仍可阅读；不得清空页面、删除原文、回退 Demo 或伪造更新时间。
9. **版本可追溯。** 原文修订后，旧中文版本保留在历史；当前版本显示“译文待更新”，直至新中文版本形成。已发布快照不可变。
10. **当前能力不伪装。** 所有目标态示例就近标“目标态界面示例·逐条中文对照尚未接通”；不得把示例翻译写成当前真实产物。

### 二、内容模型与卡片解剖

每条事件卡必须同时表达以下层级：

1. **中文标题**：视觉主标题；无译文时显示“暂无中文标题”，不得自动复制原文冒充中文。
2. **原文标题**：紧邻中文标题，可完整换行，标注原文语言；不可只放在悬浮提示中。
3. **中文事实摘要**：1–3 句，明确标“中文事实摘要”。
4. **中文关键变化**：1–3 条短句，适合扫描；没有时不显示空项目符号。
5. **可选开发者影响**：必须独立标“系统评估”，不可混入事实摘要。
6. **来源与事实层级**：来源名、发布时间、采集/观测时间、证据类型、置信度或待确认状态。
7. **中文形成信息**：形成方式、中文版本、策略版本、形成时间、当前状态。
8. **原文入口**：“查看原文证据”使用外链图标并说明将打开外部站点。

紧凑卡默认采用“中文优先但原文始终可见”：中文标题下直接显示原文标题；中文摘要下提供“展开原文摘要”。不得用只显示中文的卡片完全遮蔽原文。详情页在宽屏并排、窄屏上下排列。

### 三、核心页面

#### 1. 今日雷达 `/today`

- 顶部真相栏延续当前日期、快照、最近成功刷新、来源覆盖和新鲜度，不因中文处理状态改写新闻真相。
- 增加紧凑“中文对照覆盖”状态：事件总数、人工译文、机器翻译、规则生成、生成中、失败、待更新、无译文；明确“覆盖率不等于翻译质量”。
- 事件卡使用中文标题 + 原文标题 + 中文事实摘要 + 形成方式标签。
- 允许按“全部/有中文/待更新/失败/无译文”筛选；筛选结果数量和条件可读。
- 页面级处理失败只显示独立提示，不遮挡真实新闻列表。

#### 2. 全部事件 `/events`

- 搜索同时匹配中文与原文；结果中高亮命中语言，提示“命中中文”或“命中原文”。
- 筛选包含日期、来源、事件类型、事实层级、中文状态、形成方式；形成方式为互斥单选或明确多条件并集，不混淆状态。
- 列表密度允许舒适/紧凑两档，但两档都保留中文标题、原文标题、来源、时间、中文状态。
- 批量状态只用于浏览统计，不设计批量生成、编辑、发布或删除写操作。

#### 3. 事件详情 `/events/:eventId`

- 桌面采用双栏：左侧“中文对照”，右侧“原文与证据”；两栏顶端共享事件身份、revision、来源与时间。
- 1024 以下改为上下结构：先中文，后原文；提供可见锚点“跳到原文”“返回中文对照”，不是隐藏标签页。
- 中文区依次展示中文标题、事实摘要、关键变化、可选系统评估、形成方式、版本和状态。
- 原文区展示原始标题、原始摘要/正文摘录、来源观点、原始链接和证据时间；遵守版权限制，不复制超出授权的正文。
- 差异与修订区展示“原文 revision → 中文 revision”的明确连线；原文已变而中文未更新时，在中文区顶部显示“原文已更新，译文待更新”。
- “系统评估”必须有独立底色、图标和标题，不得像来源事实。

#### 4. 趋势与版本下钻 `/trends`

- 趋势图本身继续使用真实结构化数据；中文仅翻译图表标题、轴名、图例、事件注释和解释文案，不翻译模型名、版本号、tag、commit。
- 点选图表标记后的下钻卡显示中文事件标题、原文标题、来源和形成方式；无中文时明确“暂无译文”。
- 图表必须有完整简中等价表；表格保留原始专有字段，不以中文别名取代原值。
- 不把中文处理覆盖率画成市场份额、来源质量或新闻数量趋势。

#### 5. 开源与发布 `/open-source`

- 卡片中仓库名、owner/repo、tag、commit、许可证、API/SDK、模型 ID 原样显示；中文只解释事件事实和关键变化。
- “开源”“开放权重”“source-available”继续使用各自准确含义，不因中文翻译合并概念。
- 发布事件必须保留 breaking/effective date、版本证据和开发者动作来源；系统推导的影响单列“系统评估”。

#### 6. 历史快照与修订

- 快照页显示当时已发布的原文 revision 与中文 revision，不用今天的新译文覆盖历史画面。
- 时间线区分“原文首次发布”“原文修订”“中文版本形成”“中文版本更新”“中文处理失败”。
- 历史旧事件尚未补齐时显示“历史译文待补齐”，并保留原文可读。
- 支持查看某次修订的原文与中文配对；当前版本和历史版本有清晰标记。
- 不设计静默覆盖、删除历史或跨快照替换。

#### 7. 来源与质量说明

- 继续展示新闻来源覆盖、连接状态、新鲜度和证据质量；中文处理健康度另起一组，不混入来源健康。
- 明确“来源成功、中文处理局部失败”属于新闻可用但中文降级。
- 质量说明用短句解释形成方式、待更新机制、专有名词保真和原文核对原则。

### 四、状态系统

为以下状态分别提供组件、页面反馈和事件卡样例，文字、图标、形状、边框至少两种编码，不只靠颜色：

| 状态 | 用户文案 | 画面要求 |
|---|---|---|
| 人工译文 | `人工译文` | 人形/校对图标；显示版本与更新时间 |
| 机器翻译 | `机器翻译` | 机器图标；不使用“已核验”暗示 |
| 规则生成 | `规则生成` | 规则/节点图标；适合固定格式字段 |
| 无译文 | `暂无译文` | 原文完整保留；中文区域是明确空态 |
| 处理中 | `译文生成中` | 局部骨架屏或进度状态，不阻塞新闻 |
| 待更新 | `原文已更新，译文待更新` | 显示对应原文 revision；旧译文标为旧版 |
| 局部失败 | `部分译文生成失败` | 已成功内容照常显示；列出受影响数量 |
| 单条失败 | `译文生成失败` | 原文可读，提供状态说明；不设计本轮写操作 |
| 超时 | `译文处理超时` | 与失败区分；保留上次有效中文版本（如有） |
| 服务不可用 | `中文处理服务暂不可用` | 新闻列表和原文仍可浏览 |
| 历史待补齐 | `历史译文待补齐` | 仅影响旧事件，不伪装成当前失败 |
| 译法待确认 | `译法待确认` | 就近关联原词，不把不确定译法当确定事实 |

状态行为规则：

- `暂无译文` 是明确结果，不等于加载中；
- `译文生成中` 不显示伪进度百分比；
- `译文待更新` 必须同时展示原文已更新的时间或 revision；
- 有旧有效中文版本时，新处理失败可显示旧版，但必须显著标“旧版译文”；
- 中文状态不可改变新闻的 `live/empty/not_ready/stale/degraded/failed` 真相状态；两套状态分层展示。

### 五、交互规范

1. 默认阅读顺序为中文标题、原文标题、中文摘要、证据与状态；详情页允许通过锚点快速跳转，但不永久隐藏原文。
2. “展开原文摘要/收起原文摘要”按钮具有明确展开状态、焦点保持和读屏播报。
3. 搜索命中原文或中文时，结果页保留查询词、筛选条件和返回上下文。
4. 打开外链前以无障碍名称说明来源域名和新窗口行为；不把外部不可信内容渲染成站内系统文案。
5. revision 切换后同步更新原文、中文、版本、状态和时间，并用 `aria-live="polite"` 播报上下文变化。
6. 本轮仅设计只读浏览、搜索、筛选、排序、展开、下钻和历史切换；不新增编辑译文、人工确认、重新生成、发布、删除或批处理能力。

### 六、视觉方向与组件

- 继承浅灰画布、白色卡片、靛蓝主色、青绿强调、轻阴影和中等圆角；整体克制、专业、内容优先。
- 中文标题和原文标题使用字号、字重、间距形成主次，不用国旗图标代表语言。
- 形成方式标签使用中性轮廓样式；事实层级标签使用另一套图标与填充样式；状态告警使用独立图标和边框。
- 设计可复用组件：双语事件卡、双栏详情、原文折叠区、形成方式标签、中文状态条、revision 配对节点、术语保真标记、历史时间线、中文覆盖摘要、局部失败提示。
- 长版本号、URL、commit、代码和中英文混排不得挤压布局：允许断行或横向滚动的代码容器，但正文页面不得整体横向滚动。
- 不用大面积渐变、装饰插画、巨型数字或大段品牌文案抢占新闻内容空间。

### 七、响应式

#### 1440 桌面

- 完整全局导航和筛选；列表可使用双栏信息密度。
- 详情页中文/原文并排，单栏宽度保证中文每行约 28–42 字、英文约 60–80 字符。

#### 1024 平板/窄桌面

- 筛选进入可展开面板；详情双栏可按内容宽度切为上下排列。
- 所有状态、形成方式、来源和时间仍可见，不用只剩图标。

#### 390 与 320 移动端

- 中文区在前、原文区在后；事件卡不得并排挤压。
- 正文不小于 16px，辅助文字不小于 14px，触控目标至少 44×44px。
- 状态标签可换行但不得截断核心文案；长专有名词和版本号允许安全断行。
- 筛选使用底部抽屉；抽屉可键盘关闭、读屏有名称，关闭后焦点回到触发按钮。
- 320 必须单独重排，不把 390 画面整体缩小。

#### 200% 放大

- 同一内容完整回流，无横向页面滚动、遮挡、裁切或信息丢失；不可用缩略字抵消放大。
- 中文与原文关系、形成方式、状态和外链仍可理解。

### 八、无障碍与语言语义

1. 页面根语言为简体中文；原文片段按实际语言设置 `lang`，混合内容不得一律标中文。
2. 标题层级连续；形成方式、状态、事实层级使用可读文字，不依赖色彩或 emoji。
3. 键盘可完成导航、搜索、筛选、展开原文、进入详情、切换 revision、打开外链和返回。
4. 焦点环对比清晰且不被裁切；动态状态、筛选结果数、revision 切换使用礼貌播报。
5. 正文与小字对比度至少 4.5:1，大字至少 3:1；焦点和非文本控件至少 3:1。
6. 读屏名称需区分“中文标题”“原文标题”“中文形成方式”“中文状态”“来源事实”“系统评估”。
7. 代码、路径和版本使用适合复制阅读的字体与断行策略；不要把标点拆成不可理解的独立读屏节点。
8. 图表提供与可视标记一一对应的简中等价表，保留原始专有值。

### 九、设计演示数据标识

- 如需展示示例中文内容，每个相关画板顶部固定真相条：`目标态界面示例·逐条中文对照尚未接通`。
- 示例事件就近标 `界面演示内容`；不得使用“实时”“已生成”“已核验译文”等会暗示真实运行的字样。
- 当前真实新闻数据与示例中文内容必须视觉分区；示例不得写入当前来源覆盖、快照时间或运行健康度。
- manifest/设计说明应记录每个示例的用途、状态和非真实声明。

### 十、设计模型必须交付的内容

1. 一页增量设计系统：双语排版、标签、状态、revision、外链、错误、空态、骨架屏和焦点状态。
2. 今日雷达、全部事件、事件详情、趋势下钻、开源发布、历史快照/修订、来源与质量共 7 类核心页面。
3. 1440 和 1024 关键页面；390 与 320 至少覆盖列表、详情、筛选、待更新、失败/无译文和历史修订。
4. 一张完整状态板，覆盖本 Prompt 十二种中文形成/处理状态，并展示与新闻真实性状态的双层组合。
5. 一条可达交互流程：今日卡片 → 详情 → 原文证据 → revision 历史 → 返回原列表上下文。
6. 页面/组件/状态/断点/无障碍标注和前端验收映射；静态稿不能声明已验证真实键盘、读屏或运行时播报。

### 十一、验收标准
