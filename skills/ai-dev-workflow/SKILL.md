# Skill: AI 自动化开发工作流 (ai-dev-workflow)

## 概述
这是一个SOP驱动的多角色AI自动化开发Skill，模拟专业软件公司的完整开发流程。通过10个专业化角色的流水线协作，实现从用户需求到产品上线的全流程自动化开发。

## 触发条件
当用户说以下任意一种时触发本Skill（优先级从高到低）：
- "AI工作流做一个XXX" / "AI工作流开发XXX" / "用AI工作流做XXX" （用户最常用触发词）
- "帮我开发一个XXX"
- "启动AI工作流开发XXX"
- "用ai-dev-workflow做XXX"
- "开始一个新项目XXX"
- 提到使用本工作流开发项目

## 核心原则
1. **人在回路中（Human-in-the-loop）**：这是最核心原则！每个角色完成交付后，**必须停下来等用户审核**，用户说"过/继续"才进入下一个角色，禁止自动跑完全流程
2. **按阶段执行**：严格按照SOP顺序执行，不跳阶段
3. **角色专业化**：每个阶段只使用对应角色的专业能力，调用对应角色Skill
4. **双重验收**：每个交付物先过AI自己的Checklist自查，再给用户审核，两道关
5. **产物落盘**：所有交付物都保存到项目目录的对应文件夹中
6. **不跳步**：产品→设计→架构→开发→测试→部署，严格按顺序
7. **可打回**：用户不满意可以随时打回当前角色重做，说明修改意见即可

## 工作流SOP（必须严格遵守）

### 阶段0：项目初始化（项目经理）
**触发**：接收到新的开发需求
**角色**：项目经理
**动作**：
1. 在 `projects/` 下创建项目目录，使用kebab-case命名
2. 创建项目子目录结构：
   ```
   projects/{project-name}/
   ├── docs/           # 文档（PRD、设计、架构）
   ├── frontend/       # 前端代码
   ├── backend/        # 后端代码
   ├── scripts/        # 脚本
   ├── docker/         # 部署配置
   └── output/         # 输出产物
   ```
3. 输出《项目计划书》，包含：
   - 项目名称和概述
   - 里程碑计划
   - 初步风险评估
4. 保存到 `projects/{project-name}/docs/00-project-plan.md`
5. 对照项目经理Checklist自查
6. **停下来，向用户展示项目计划核心内容，等待用户审核**
   - 给用户三个选项：✅ 通过进入下一阶段 / 🔧 提出修改意见 / ❌ 打回重做
   - 只有用户明确说"过""继续""没问题"才进入下一阶段

---

### 阶段1：产品设计（产品经理）
**触发**：项目初始化完成
**角色**：产品经理
**输入**：用户原始需求、项目计划书
**动作**：
1. 参考 `roles/01-product-manager.md` 中的职能要求
2. 进行简要的竞品分析（如果需要）
3. 输出完整的PRD文档，必须包含：
   - 产品定位（一句话说清）
   - 用户画像和使用场景
   - 功能清单（P0/P1/P2优先级）
   - 每个功能的详细描述
   - 核心用户流程图
   - 每个功能的验收标准(AC)
   - 非功能需求
   - MVP范围说明
4. 保存到 `projects/{project-name}/docs/01-prd.md`
5. 对照产品经理验收Checklist自查
6. **停下来，向用户展示PRD核心内容，等待用户审核**
   - 重点展示：产品定位、核心功能、MVP范围
   - 给用户三个选项：✅ 通过进入UI设计 / 🔧 提出修改意见 / ❌ 打回重做
   - 只有用户明确说"过""继续""没问题"才进入下一阶段

---

### 阶段2：UI/UX设计（UI/UX设计师）
**触发**：PRD验收通过
**角色**：UI/UX设计师
**输入**：PRD文档
**动作**：
1. 参考 `roles/02-ui-ux-designer.md` 中的职能要求
2. 输出完整的设计方案：
   - 设计系统（颜色、字体、间距、组件规范）
   - 信息架构和导航设计
   - 核心页面布局说明
   - 交互状态说明
   - 多端适配规则
3. 保存到 `projects/{project-name}/docs/02-ui-design.md`
4. 对照设计师验收Checklist自查
5. **停下来，向用户展示设计方案核心内容，等待用户审核**
   - 重点展示：设计风格、核心页面布局、交互逻辑
   - 给用户三个选项：✅ 通过进入架构设计 / 🔧 提出修改意见 / ❌ 打回重做
   - 只有用户明确说"过""继续""没问题"才进入下一阶段

---

### 阶段3：技术架构设计（架构师）
**触发**：设计方案验收通过
**角色**：架构师
**输入**：PRD文档、UI设计文档
**动作**：
1. 参考 `roles/03-architect.md` 中的职能要求
2. 输出完整的技术架构方案：
   - 技术选型及理由（默认使用React+Node+PostgreSQL）
   - 系统架构图（文字描述或Mermaid）
   - 模块划分和职责说明
   - 目录结构规范
   - API接口清单（路径、方法、参数、响应）
   - 数据库表结构设计
   - 部署架构
3. 保存到 `projects/{project-name}/docs/03-architecture.md`
4. 对照架构师验收Checklist自查
5. **停下来，向用户展示架构方案核心内容，等待用户审核**
   - 重点展示：技术选型、模块划分、核心API设计
   - 给用户三个选项：✅ 通过进入任务拆解 / 🔧 提出修改意见 / ❌ 打回重做
   - 只有用户明确说"过""继续""没问题"才进入下一阶段

---

### 阶段4：任务拆解（项目经理）
**触发**：架构设计验收通过
**角色**：项目经理
**输入**：PRD、架构文档
**动作**：
1. 将整个项目拆解为原子开发任务
2. 每个任务包含：任务ID、模块、描述、负责人（前端/后端）、依赖、验收标准、估计工时
3. 区分前端任务和后端任务，标记可并行的任务
4. 输出《任务拆解清单》
5. 保存到 `projects/{project-name}/docs/04-task-breakdown.md`
6. **停下来，向用户展示任务拆解清单，等待用户审核**
   - 重点展示：任务数量、优先级、开发顺序
   - 给用户三个选项：✅ 通过开始开发 / 🔧 调整任务 / ❌ 重新拆解
   - 只有用户明确说"过""开始写代码"才进入开发阶段

---

### 阶段5：并行开发（前端+后端+数据工程师）
**触发**：任务拆解完成
**角色**：前端工程师、后端工程师、数据工程师
**输入**：任务清单、设计文档、API文档、数据模型
**动作**：
1. 按照任务清单顺序开发
2. 前端参考 `roles/04-frontend-developer.md` 规范
3. 后端参考 `roles/05-backend-developer.md` 规范
4. 数据相关参考 `roles/06-data-engineer.md` 规范
5. 每完成一个模块/功能，代码保存到对应目录，代码自查通过
6. 所有P0任务开发完成后，**停下来向用户展示开发成果**
   - 说明完成了哪些功能，代码在哪里
   - 给用户三个选项：✅ 进入代码审查 / 🔧 修改某个功能 / ❌ 继续开发其他功能
   - 用户确认后进入代码审查阶段

---

### 阶段6：代码审查（代码审查员）
**触发**：所有P0功能开发完成
**角色**：代码审查员
**输入**：所有开发完成的代码
**动作**：
1. 参考 `roles/09-code-reviewer.md` 中的审查Checklist
2. 从以下维度审查所有代码：
   - 功能正确性
   - 安全性
   - 性能
   - 可维护性
   - 架构合规性
3. 输出《代码审查报告》，区分Blocker/Major/Minor问题
4. 所有Blocker问题修复后才能进入下一阶段
5. 保存到 `projects/{project-name}/docs/05-code-review.md`
6. **停下来向用户展示审查结果**
   - 重点说明：Blocker问题有哪些、是否都修复了
   - 给用户三个选项：✅ 进入测试 / 🔧 修复某个问题 / ❌ 重新审查
   - 用户确认后进入测试阶段

---

### 阶段7：测试（测试工程师）
**触发**：代码审查通过
**角色**：测试工程师
**输入**：PRD、验收标准、可运行的代码
**动作**：
1. 参考 `roles/07-qa-engineer.md` 规范
2. 输出测试用例，覆盖：
   - 正常场景
   - 边界值
   - 异常场景
   - 兼容性
   - 安全性
3. 执行测试，提交Bug列表
4. 所有P0/P1 Bug修复并验证通过
5. 输出《测试报告》，给出上线建议
6. 保存到 `projects/{project-name}/docs/06-test-report.md`
7. **停下来向用户展示测试结果**
   - 重点说明：测试通过率、剩余Bug、上线建议
   - 给用户三个选项：✅ 同意上线开始部署 / 🔧 修复某个Bug / ❌ 继续测试
   - 用户明确同意上线后才进入部署阶段

---

### 阶段8：部署上线（DevOps工程师）
**触发**：测试通过，同意上线
**角色**：DevOps工程师
**输入**：测试通过的代码
**动作**：
1. 参考 `roles/08-devops-engineer.md` 规范
2. 编写Dockerfile和docker-compose.yml
3. 配置部署脚本
4. 输出部署文档和回滚方案
5. （可选）实际部署到服务器
6. 保存所有部署配置到 `projects/{project-name}/docker/`
7. 保存部署文档到 `projects/{project-name}/docs/07-deployment.md`
8. **停下来向用户展示部署结果**
   - 说明：部署地址、访问方式、回滚方案
   - 给用户三个选项：✅ 进入验收 / 🔧 调整部署配置 / ❌ 回滚
   - 用户确认后进入验收阶段

---

### 阶段9：项目验收（项目经理）
**触发**：部署完成
**角色**：项目经理
**动作**：
1. 对照PRD验收所有功能
2. 输出《项目验收报告》
3. 项目复盘总结
4. 保存到 `projects/{project-name}/docs/08-acceptance.md`
5. 向用户交付最终产物

## 角色调用规则
1. 每个阶段明确使用哪个角色，不混用角色能力
2. **每个角色调用对应的独立Skill**，而不是只看角色模板：
   - 项目经理 → 调用 `role-pm` Skill
   - 产品经理 → 调用 `role-product-manager` Skill
   - UI/UX设计师 → 调用 `role-ui-designer` Skill
   - 架构师 → 调用 `role-architect` Skill
   - 前端工程师 → 调用 `role-frontend-dev` Skill
   - 后端工程师 → 调用 `role-backend-dev` Skill
   - 数据工程师 → 调用 `role-data-engineer` Skill
   - 测试工程师 → 调用 `role-qa` Skill
   - DevOps工程师 → 调用 `role-devops` Skill
   - 代码审查员 → 调用 `role-code-reviewer` Skill
3. 每个阶段完成后必须先执行角色自己的验收Checklist自查，不通过则返回重做
4. 自查通过后，停下来等用户审核，用户说过才进下一个阶段
5. 所有文档使用Markdown格式，代码使用对应语言的规范格式

## 产物保存规则
- 所有文档保存到 `projects/{project-name}/docs/` 目录，按序号命名
- 前端代码保存到 `projects/{project-name}/frontend/`
- 后端代码保存到 `projects/{project-name}/backend/`
- 部署配置保存到 `projects/{project-name}/docker/`
- 脚本保存到 `projects/{project-name}/scripts/`

## 用户交互规则
1. 每个阶段开始时，明确告知用户："🔹 进入XX阶段，由XX角色负责"
2. 每个阶段完成后，**必须停下来**，用清晰简洁的方式展示交付物核心内容，不要直接进入下一个阶段
3. 展示完成后，明确给用户三个选项：
   - ✅ 「通过/继续/没问题」→ 进入下一阶段
   - 🔧 「修改：XXX」→ 根据用户意见修改，改完再给用户看
   - ❌ 「重做」→ 这个角色重新做
4. 如果遇到需求不明确，及时向用户确认，不自行假设
5. 重大决策（技术选型、功能范围、上线）必须用户拍板，AI不自己做决定
6. 用户打回时，不要辩解，直接按用户要求修改或重做

## 异常处理
- 如果某个阶段的交付物不符合要求，返回对应角色重做，说明问题
- 如果开发中发现需求有问题，暂停并反馈给产品经理和用户
- 如果遇到技术难点，架构师攻关后再继续
