# AI 工作流框架专业性审计

审计日期：2026-07-31

## 一句话结论

当前项目是 **SOP 驱动、人在回路的 AI 软件工程工作流实验框架**，属于真正的“AI 工作流定义”，但还不是“可执行、可恢复、可观测、可评测的多 Agent 运行系统”。

综合成熟度：**L2 / 5，约 42 / 100**。

| 维度 | 判断 |
|---|---|
| 学习定位 | 清楚，适合用样本项目体验工作流结果 |
| 角色与 SOP | 基本专业，已有职责、交付和人工审核 |
| 状态与交接 | 已落地最小 YAML/JSONL 契约，但尚无运行时写入、强 Schema 与恢复机制 |
| 自动编排与恢复 | 未实现 |
| 追踪、成本、评测 | 未实现 |
| 端到端证据 | 首个样本只走通到前端原型/视觉 QA，未完成完整闭环 |
| 控制中心 | 已有专业视觉原型，但数据、导航和持久化仍是假数据/演示逻辑 |

## 已确认的专业问题

### P0：先建立可信工作流状态

- 三个项目已有最小 state、approval、artifact、event 和 Skill lock 文件；仍没有真正的运行实例、检查点服务、失败重试和恢复游标。
- 角色交接主要靠自然语言，没有可机器验证的输入输出契约。
- 控制中心的项目、阶段、角色、缺陷和同步状态目前硬编码；缺陷点击只保存在浏览器内存。
- 首个样本的后端、Docker、脚本和输出链路尚未证明，不能称已经端到端走通。

最小状态实体应覆盖：workflow definition、run、stage run、artifact、approval、task、defect、evaluation、release、audit event。

### P1：消除规范漂移

- 根目录 Skill、样本 Skill 和全局安装 Skill 是多套副本，过去没有版本号、生成器或漂移检查。
- 首个样本的文档编号和总控 SOP 不一致。
- 架构文档的 React/TypeScript/Tailwind 版本与实际代码不一致。
- 任务表状态与 Git 实际进度不一致。
- 控制中心必须只展示真实状态；未接数据前统一标“演示数据”。

本次已把根目录 `skill/` 明确为唯一规范源，把旧平铺总控文件改为兼容入口，新增 `workflow-project-init` 初始化/收编 Skill 和只读漂移检查，并让三个项目持有锁定的共享 Skill 快照；下一步仍需把漂移检查接入 CI。

### P1：从瀑布排队改为有门禁的小批量循环

- QA 应在 PRD 阶段先设计测试策略。
- DevOps 应在初始化/架构阶段建立环境与 CI。
- 代码审查应按任务持续发生。
- 开发、审查、测试和复测应小批量循环。
- 超级无敌帅超超总要求的“每个角色入场审批”已设为强制规则；长期运行后可再按风险分级，避免审批疲劳。

### P1：补 AI 与工作流工程能力

现有后端和数据角色只覆盖部分模型/RAG 能力，仍缺：

1. AgentOps / 工作流平台工程师：编排、状态机、检查点、恢复、追踪。
2. 工作流评测负责人：链路成功率、交付质量、返工、成本和时延评测。
3. AI/LLM 工程师：模型路由、Prompt/模型版本、离线评测、安全和降级。
4. 安全与隐私工程师：公网、账号、支付或敏感数据项目条件启用。

这些职位属于建议缺岗，本次未自动创建，等待超级无敌帅超超总决定是否成为固定或条件角色。

## 角色冗余判断

- 包工头与项目经理不冗余：前者治理整个实验平台和跨项目协作，后者管理单个项目。
- 项目经理与产品经理不冗余：一个管交付，一个管产品价值和范围。
- 代码审查员与 QA 不冗余：一个检查代码变更，一个验证产品行为和发布质量。
- DevOps 不冗余，但应提前参与。
- 数据工程师是条件角色：简单 CRUD 项目可由架构师和后端覆盖；复杂数据、ETL、迁移、分析和向量检索再独立启用。

## 本轮已落地

- 重新写明根项目的学习/验证定位，明确 `projects/` 是实验样本。
- 全部现有角色 Skill 加入“每次称呼超级无敌帅超超总”和“角色入场必须经超级无敌帅超超总批准”。
- 新增市场调研员 Skill，并把它放在项目经理上游。
- UI/UX Skill 增加“UI/Demo/原型/UI 审核必参与、先交提示词、批准后设计”的强制门。
- 总控 SOP 更新为 11 个核心角色、双门审批、小批量开发、持续审查、Bug 复测和工作流复盘。
- 创建并发布 `control-center/` 第一版；清楚标定为视觉原型。
- 创建 `projects/ai-model-radar/` 可追溯项目骨架，市场调研角色已获批准并开始研究。
- 新增统一项目初始化 Skill；三个项目均已采用同一治理外壳、独立项目级 Skill 和 Profile 化真实入口。
- 增加结构验证器、Skill 哈希锁和新项目双 Profile 前向测试，避免“目录看似统一但入口被破坏”。

## 建议演进顺序

1. 将已完成的 Skill 源、同步器和漂移检查接入 CI。
2. 让控制中心读取已经落地的 state、approval、artifact、event 契约。
3. 选择一个小样本完整走完调研到验收，保留每个审批和失败证据。
4. 再实现编排器、检查点、恢复、重试、追踪和真实管理界面。
5. 最后增加工作流评测、模型质量、安全、Token/费用和自动化程度治理。

## 专业基线

- [MetaGPT](https://arxiv.org/abs/2308.00352)：SOP 编码与专业角色协作。
- [ChatDev](https://arxiv.org/abs/2307.07924)：角色化沟通链。
- [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/)：工具、交接、护栏、会话、人在回路和追踪。
- [OpenAI Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)：可序列化运行状态和暂停/恢复审批。
- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：检查点、持久化和故障恢复。
