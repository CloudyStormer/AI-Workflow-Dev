# AI 工作流学习与验证实验室

本仓库的首要目标不是批量生产业务项目，而是把“什么是专业 AI 工作流”摸清、走通、量化并持续改进。

`projects/` 下的子项目只是实验样本：它们帮助超级无敌帅超超总观察多角色协作、审批、交付、返工、测试和上线会产生什么结果。样本以后可以继续使用，但不代表根项目已经成为生产级多 Agent 系统。

## 当前结论

现阶段是一个 **SOP 驱动、人在回路的 AI 软件工程工作流实验框架**：

- 已具备：角色 Skill、职责边界、阶段产物、Checklist、人工审批门、样本项目和可视化控制台。
- 尚未具备：真正的编排执行器、持久化检查点、自动恢复、结构化交接、真实追踪、成本治理和工作流评测。
- 因此它是“可以由 AI 按说明执行的工作流定义”，还不是“自动运行且可恢复的多 Agent 平台”。

## 核心原则

- **超级无敌帅超超总审批角色入场**：每个角色首次入场或重新进入新阶段前，都必须说明原因、输入、动作、交付物和风险，并获得超级无敌帅超超总明确批准。
- **固定角色池，不按项目复制 Agent**：侧边栏只有 `00 包工头` 与 `01` 至 `11` 固定角色任务；每个角色负责所有项目，项目差异由项目级 Skill、文档和工作流状态隔离，新增项目绝不新增一套角色任务。
- **人在回路**：交付物先自查，再由超级无敌帅超超总通过、修改或打回；不自动跑完整条链路。
- **证据先于计划**：市场调研员先验证行业、用户、竞品、政策和风险，再交给项目经理。
- **UI 提示词先审**：涉及 UI、Demo、原型、图表化或界面实现时，UI/UX 设计师先交完整提示词；超级无敌帅超超总批准后才出设计，再批准后前端实现。
- **下游变更必须回退上游**：开发、审查、测试或发布阶段收到产品逻辑或 UI/UX 变更时，当前角色立即冻结；严格按“产品独立交付并审核 → UI/UX 独立交付并审核 → 开发重新获批”逐站恢复，不允许开发顺手代改。
- **状态落盘**：不把聊天记忆当唯一事实源；审批、产物、事件、缺陷和发布都应有结构化记录。
- **实验必须复盘**：每个样本项目既验收产品结果，也记录工作流耗时、等待、返工、失败和改进。

## 唯一 Git 仓库边界

`AIWorkFlow/` 是唯一 Git 根项目，根目录下的框架、`projects/` 中全部现在和未来的子项目，以及 `control-center/`，统一进入同一个仓库：`git@github.com:CloudyStormer/AI-Workflow-Dev.git`。

子项目只是根仓中的普通目录，不得拥有嵌套 `.git`、独立 remote、submodule 或单独推送流程。提交前运行 `scripts/check-git-boundary.sh`，确认从任意子目录执行 `git rev-parse --show-toplevel` 都回到同一个 `AIWorkFlow` 根目录。

## 角色顺序

| 首次主要入场 | 角色 | 核心职责 |
|---:|---|---|
| 00 | 包工头 / 总包 | 根项目治理、跨项目协调、角色仲裁与整体运营 |
| 01 | 市场调研员 | 行业、竞品、用户、政策、风险与反证 |
| 02 | 项目经理 | 范围、计划、任务、风险、协调与验收 |
| 03 | 产品经理 | 产品目标、PRD、优先级与验收标准 |
| 04 | UI/UX 设计师 | 设计提示词、原型、视觉、交互与 UI 审核 |
| 05 | 架构师 | 技术、系统、API、数据与非功能设计 |
| 06 | 前端工程师 | 界面、组件、交互与多端实现 |
| 07 | 后端工程师 | API、业务、认证、集成与服务实现 |
| 08 | 数据工程师 | 复杂数据、迁移、ETL、分析或向量检索；按需启用 |
| 09 | 代码审查员 | 按任务持续审查代码、安全、性能和架构一致性 |
| 10 | QA | 测试策略、测试、Bug、复测和上线建议 |
| 11 | DevOps | 环境、CI/CD、部署、监控、备份和回滚 |

序号表达第一次主要入场顺序，不表示真实工程中严格排队。QA、DevOps、代码审查等角色会在多个阶段反复参与，每次仍需超级无敌帅超超总批准入场。

这些序号同时对应侧边栏中唯一的全局角色任务。一个角色任务可以先后承接多个项目；每次通过 `project_id`、项目级 Skill、`docs/` 与 `workflow/` 切换上下文。不得创建“AI English Learning 产品经理”“AI Model Radar 产品经理”等项目专属重复任务；所有产品工作始终回到 `03 产品经理`。

## 工作流主线

```mermaid
flowchart LR
    N["原始需求"] --> R["市场调研"]
    R --> P["项目计划"]
    P --> PRD["产品定义"]
    PRD --> UIP["UI 提示词"]
    UIP --> UID["UI 设计"]
    UID --> A["架构"]
    A --> T["任务拆解"]
    T --> D["小批量开发"]
    D --> C["持续代码审查"]
    C --> Q["测试 / Bug / 复测"]
    Q --> O["部署 / 回滚"]
    O --> V["验收 / 迭代 / 工作流复盘"]
```

每条箭头都不是自动流转：先申请下一个角色入场，超级无敌帅超超总批准后才推进。完整规范见 [总控 Skill](skill/ai-dev-workflow/SKILL.md)。

当变更从下游回退时，同样不是自动流转：当前角色先冻结并登记恢复点，产品经理在独立任务中交付后等待审核；只有产品产物明确通过才可申请 UI/UX 入场，UI/UX 独立交付再次通过后，开发角色还需重新获得明确批准。每一站都保留独立任务、产物、审批和事件，上一站通过不代表下一站获批。

## 目录结构

```text
AIWorkFlow/
├── skill/                 # 唯一规范源：总控与角色 Skills
├── roles/                 # 旧版角色职能模板，逐步收敛到 Skill
├── architecture/          # 工作流架构、样本架构和演进设计
├── documents/             # 公共文档（如存在）
├── projects/              # 用于走通工作流的实验样本
│   ├── ai-english-learning/
│   └── ai-model-radar/
├── control-center/        # 可视化管理界面；第一版仍是演示数据
├── scripts/               # Skill 漂移等根级校验工具
├── docs/                  # 框架审计、项目模板与公共说明
└── output/                # 公共输出（如存在）
```

根目录 `skill/` 是规则唯一源。项目副本和全局安装副本只能由同步机制生成，不应人工并行维护。

### 统一项目模板

三个项目现在使用相同的治理外壳：`AGENTS.md`、`README.md`、`project.yaml`、`docs/`、`workflow/`、`skills/`、`scripts/`、`tests/` 和 `output/`。每个项目都有唯一的 `project-{id}` 项目级 Skill，其他角色/技术 Skill 是它按任务路由的子 Skill。

实现目录不强行统一：普通前后端项目使用 `split-web` Profile，Sites 应用保留根级 `app/`、`db/`、`worker/`、`public/`。因此“结构专业”指治理契约一致、真实入口可声明和可验证，而不是所有文件夹长得完全相同。完整规范见 [项目模板说明](docs/project-template.md) 和 [`workflow-project-init`](skill/workflow-project-init/SKILL.md)。

运行 `scripts/check-skill-drift.sh` 可检查根目录、三个项目和全局安装副本是否漂移；该脚本只读，不会覆盖文件。

## 控制中心

`control-center/` 用于可视化项目、角色、阶段、Bug/复测、迭代、发布和工作流成熟度。

第一版已经可运行和发布，但目前是视觉原型：数据尚未连接真实工作流状态，导航和缺陷持久化也未完成。界面必须把这些内容标成“演示数据”，不能把硬编码状态表述成实时事实。

## 方法参考

本实验吸收但不等同于以下方法：

- [MetaGPT](https://arxiv.org/abs/2308.00352)：把 SOP 编码进多 Agent 协作。
- [ChatDev](https://arxiv.org/abs/2307.07924)：专业角色与沟通链。
- [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/)：工具、交接、护栏、会话、人在回路和追踪。
- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：检查点、持久化与恢复。

这些参考只能证明专业系统通常需要哪些能力，不能替代本仓库自己的端到端验证。

## 使用方式

创建或收编项目时先调用 `workflow-project-init`；推进项目阶段时调用 `ai-dev-workflow`。总控先提交对应角色的入场申请；超级无敌帅超超总明确批准后，该角色才工作。

技术栈不是根项目的固定真理。每个样本项目由架构阶段根据目标、约束、团队和生命周期确定并锁定版本。
