## 二、完整设计提示词

你是一名资深企业级数据产品 UI/UX 设计师。请为“AI Workflow Control Center”设计下一版高保真 Web 控制中心，并形成可点击原型。

### 1. 产品定位

这是一个 SOP 驱动、人在回路的 AI 软件工程工作流实验与验证平台。

根项目负责工作流方法、角色、审批、质量、恢复与成熟度治理；projects 下的项目是用于验证流程的实验样本，不应把产品表达成批量生产业务项目的流水线工厂。

### 2. 主要用户

#### 第一用户：项目所有者“超级无敌帅超超总”

- 快速判断项目是否正常、哪里阻塞、下一项需要批准什么。
- 查看质量、复测、迭代、发布和工作流成熟度。

#### 第二用户：项目经理、QA、DevOps 和各专业角色

- 查看自身任务、阶段、交接、缺陷、门禁和证据。

#### 观察用户：团队成员

- 了解 AI 软件工程工作流的运行状态、风险和改进方向。

### 3. 核心体验目标

用户进入控制中心后，应在 10 秒内回答：

1. 当前有多少项目，分别进行到什么阶段？
2. 哪个项目或阶段被阻塞？
3. 当前由哪些角色工作，谁在等待、阻塞或待审批？
4. Bug 分布如何，有多少正在修复、待复测或已关闭？
5. 当前迭代完成度和范围变化如何？
6. 是否具备发布条件，哪项发布门禁未通过？
7. 工作流成熟度是多少，最薄弱的能力在哪里？

### 4. 改版原则

1. 显著减少说明性大段文字。
2. 用图表、状态图、阶段矩阵、时间线和可视化门禁代替文字陈述。
3. 每张卡片正文最多两行，详细原因进入 Tooltip、Popover 或右侧详情抽屉。
4. 所有汇总数字必须由明细计算，不允许总分与子项不一致。
5. 不使用装饰性 3D 图表、无意义渐变、复杂网络背景或仪表盘堆砌。
6. 视觉应专业、克制、高信息密度，但不能拥挤。
7. 所有静态样例必须标为“演示数据”，不能伪装成实时状态。

### 5. 真实监管数据模式与顶层状态契约（v1.1 强制新增）

所有页面必须在首个可视区域显示统一“监管数据状态条”，不能只在设置页或 Tooltip 中说明。状态条包含：

- 服务健康：`健康`、`不健康`、`未知`；
- 数据就绪：`就绪`、`降级可用`、`未就绪`；
- 数据模式：`真实根仓观测`、`上次成功快照`、`静态回退／演示数据`；
- 覆盖：成功项目数／登记项目总数、失败项目数；
- 本次观测时间 `observed_at`；
- 最近成功观测时间；
- 根仓提交 `HEAD`；
- 工作树：`clean`、`working-copy-modified`、`unknown`；
- “查看来源与错误”入口。

严格区分以下数据模式：

| 数据模式 | 中文主标签 | 页面行为 |
|---|---|---|
| `live-repository` | 真实根仓观测 | 仅在本次确实完成根仓读取时显示；展示本次观测时间、HEAD、覆盖和来源 |
| `degraded-live` | 部分项目读取失败 | 保留成功项目，显著列出失败项目、失败数据域和最近成功时间；不能显示“全部正常” |
| `stale-memory` | 上次成功快照 · 已过期 | 当前读取失败但内存中有上一版时使用；显示快照时间、失败时间、失败原因和重新读取入口 |
| `static-fallback` | 静态回退 · 非实时 | 使用前端内置内容时使用；不能贡献真实监管汇总，所有卡片继续标“演示数据”或“待接入” |
| `not-ready` | 数据未就绪 | 没有任何有效根仓观测时使用；不以静态项目清单、空数组或全零指标冒充成功 |

服务健康与数据就绪是两条独立轴：

| 服务健康 | 数据就绪 | 必须表达的含义 |
|---|---|---|
| 健康 | 就绪 | 服务可响应，全部登记项目必需治理文件完成本次观测 |
| 健康 | 降级可用 | 服务可响应，但一个或多个项目／数据域失败；可用结果与失败范围同时展示 |
| 健康 | 未就绪 | 服务进程存活，但根仓不可识别、项目清单无法形成或没有有效观测 |
| 不健康／离线 | 有上次快照 | 当前服务不可用；旧快照只能按其真实时间只读展示，不能写“实时”或“刚刚更新” |
| 不健康／离线 | 无有效快照 | 显示服务不可用和恢复建议，不显示伪项目数据 |

禁止用一个绿色圆点同时代表服务健康、数据完整、来源新鲜和项目无风险。

### 6. 来源、新鲜度与逐条追溯（v1.1 强制新增）

每张汇总卡、图表、表格和详情抽屉都必须能追溯到构成记录。紧凑视图显示“来源类型 + 新鲜度”，展开后至少显示：

- 根仓内相对 `source_path`，不得回显根仓外绝对路径；
- `source_sha256`；
- `source_updated_at`，缺失时明确“源更新时间未知”；
- `observed_at`；
- `root_head`；
- `working_tree_state`；
- `freshness=current / stale / unknown`；
- `coverage=complete / partial / not_available`；
- 错误代码、影响范围和可执行恢复说明。

`observed_at` 只表示服务读取时间，不能替代业务记录更新时间。来源更新时间缺失时不显示“刚刚更新”。登记哈希与当前文件哈希不一致时并列显示“登记版本”和“当前工作副本”，标记 `hash_mismatch`，不自动修复或判断新文件已批准。

### 7. 空、未知、错误与降级状态（v1.1 强制新增）

至少输出以下状态组件和组合页面，不得合并成一个通用空状态：

1. 首次加载，无历史数据；
2. 刷新中，继续显示上一份有效快照；
3. 查询成功且真实数量为 0；
4. 数据域未登记，`coverage=not_available`；
5. 条件筛选无匹配；
6. 单项目治理文件缺失；
7. 单项目解析失败；
8. JSONL 单行损坏、其余事件仍可用；
9. 多项目部分失败，整体 `degraded`；
10. 根仓不可定位／不可读，整体 `not_ready`；
11. 最近读取失败但有上次成功快照；
12. 最近读取失败且没有有效快照；
13. 来源记录时间未知；
14. 读取过程中 HEAD 或文件哈希发生变化，标“本次观测不一致，请重新读取”；
15. 登记哈希与当前文件不一致；
16. 高优先级来源之间冲突，标 `conflict` 并列证据；
17. 工作树存在未提交修改；
18. 审批 `not_recorded`，不能显示“已拒绝”；
19. 问题覆盖不可用，不能显示“0 个问题”；
20. 只有发布方案或 URL、没有成功部署／健康证据。

错误组件必须同时包含：发生了什么、影响哪些项目／数据域、仍可使用什么、最后成功时间和下一步。不得因一项失败遮挡其他项目的可用数据。

- X 轴：日期或迭代。

- 0–1 天、2–3 天、4–7 天、7 天以上。

- Blocker 是否归零

- 测试报告是否存在
- 发布建议是否获得批准

#### 缺陷明细

- ID、标题、严重度、模块、负责人、状态、创建时间、修复时间、复测结果。
- 默认使用紧凑表格。
- 移动端改为卡片列表。
- 不允许仅凭颜色表达严重度。
- 没有统一结构化问题登记时显示“问题覆盖不可用”，不得把空集合写成“0 个问题”。

- 自动化测试
- 安全检查
- 备份与回滚
- 监控与日志
- 超级无敌帅超超总发布授权

#### 发布详情抽屉

- 版本变更
- 关联 Bug
- 门禁证据
- 健康检查
- 回滚点
- 审批记录

总成熟度只有在六个维度、权重和证据均已结构化登记时才计算，并允许查看公式。缺少规则或证据时显示“成熟度暂不可计算”，不得根据目录存在、阶段编号或手工印象生成伪精确分数。

## 六、图表与数据映射

### 1. 项目阶段矩阵

- 行：projectId/projectName
- 列：stageOrder 0–10
- 单元格颜色：stageStatus
- 图标：approvalStatus
- 边框：isCurrentStage
- Tooltip：owner、evidenceCount、blockedReason、updatedAt

### 2. 阶段流水线

- 节点顺序：stageOrder
- 节点状态：done/active/risk/blocked/pending-approval/waiting
- 节点负责人：ownerRole
- 连线状态：handoffStatus
- 节点徽标：artifactCount、approvalStatus

### 3. 角色负载图

- Y 轴：roleName
- X 轴：taskCount
- 堆叠：todo/inProgress/review/testing/done
- 风险标记：blockedCount
- 辅助信息：approvalWaitingTime

### 4. 缺陷堆叠图

- X 轴：issueStatus
- 堆叠：severity
- 值：issueCount
- 点击结果：筛选缺陷明细

### 5. 复测趋势

- X 轴：date/iteration
- Y 轴：retestPassRate
- 计算：passed / (passed + failed)
- 同时展示 passed、failed、notRun

### 6. 迭代燃尽

- X 轴：iterationDay
- Y 轴：remainingWork
- 折线：idealRemaining、actualRemaining
- 标记：scopeAdded、scopeRemoved

### 7. 发布就绪度

- 维度：build、test、security、rollback、monitoring、approval
- 实际值：readinessScore
- 目标线：requiredScore
- 状态：pass/warn/fail/notAvailable

### 8. 成熟度雷达

- 轴：六个成熟度维度
- 值：dimensionScore，范围 0–100
- 总分：weightedAverage
- 对比：currentIteration 与 previousIteration

所有图表必须：

- 有标题、单位、图例和数据来源。
- Hover 显示精确值和计算口径。
- 支持键盘访问。
- 提供“查看数据表”替代入口。
- 不以面积或角度表达难以比较的精确小数。
- 不让同一种颜色跨页面表达不同含义。
- 显示数据模式、覆盖、新鲜度、本次观测时间和根仓 HEAD；部分覆盖时说明缺少哪些项目或数据域。
- 当来源为 `static-fallback` 时整张图标注“静态回退 · 演示数据”，不得与真实根仓数据合并计算。

2. 每张图表右上角显示来源徽标：真实数据、演示数据、待接入或混合来源。
3. 演示数据使用紫色标签或轻微点状纹理，不使用绿色“已同步”状态。

   - workflow/approvals.yaml
   - workflow/artifacts.yaml
   - workflow/events.jsonl
   - 测试报告
   - 发布记录
   - 验收与复盘记录

静态回退规范：

1. `static-fallback` 只保证页面结构可浏览，不证明真实监管服务、来源连接或项目观测成功。
2. 真实服务不可用时不得无提示自动把静态演示数据改名为真实项目数据。
3. 用户可以明确切换到静态回退，但页面顶栏、图表、表格和抽屉持续显示“静态回退 · 非实时”。
4. 静态回退的数量、趋势、问题、角色状态、发布和成熟度不得进入真实汇总。
5. 从静态回退切回真实数据时必须重新显示健康、就绪、覆盖、HEAD 和观测时间。

交互规则：

1. 图表点击后交叉筛选同页其他模块。
2. 再次点击或点击“清除筛选”恢复全量。
3. 点击图表数据点打开右侧详情抽屉。
4. URL 或页面状态保留当前项目和筛选条件。
5. Tooltip 只放精确数值和简短解释，不放长篇业务说明。
6. Control Center MVP 是只读监管界面，不提供审批、状态迁移、问题更新、发布、回滚、Git、文件修复或任意写入按钮。
7. “去处理”只能打开来源证据、关联固定角色任务说明或复制相对路径；不能在控制中心内直接改变状态。
8. 如视觉原型需要展示未来写入概念，必须使用不可操作占位并标“本版本不支持”，不能制作看似成功的模拟提交 Toast。
9. 重新读取只触发只读观测；显示进行中、成功、部分成功或失败，不得声称修复了源文件。

## 十、响应式

### 桌面端：大于 1200px

- 240px 固定侧边栏。
- 12 列网格。
- 核心图表双列或三列布局。
- 首屏高度目标为 900px，优先展示决策信号。

### 平板端：768–1200px

- 72px 图标导航，可展开。
- 8 列网格。
- 双列转单列。
- 阶段矩阵允许组件内部横向滚动，页面整体不能横向滚动。

### 移动端：小于 768px

- 顶部项目切换器。
- 底部导航：总览、项目、质量、更多。
- 单列布局。
- KPI 使用 2×N 网格。
- 雷达图提供水平条替代视图。
- 表格切换为卡片。
- 图表默认显示关键值，其余内容按需展开。
- 触控目标至少 44×44px。
- 390px 宽度下不得出现页面级横向滚动。
- 320px 宽度下仍可查看健康、就绪、数据模式、覆盖、最近成功时间和主要错误；状态条改为可展开摘要，不能完全隐藏。
- 项目、角色、审批、产物、事件、问题和发布明细在 320px 下使用定义列表／卡片，并保留来源、新鲜度、错误与只读操作。

设计输出规格：

- 6 张 1440px 桌面核心页面
- 1 张 1024px 平板总览
- 1 张 390px 移动端总览
- 1 张 390px 移动端质量与复测
- 1 张 320px 数据降级与来源详情
- 1 张组件及状态规范页

## 十一、无障碍

1. 符合 WCAG 2.2 AA。
2. 正文对比度至少 4.5:1。
3. 大字和图形关键边界至少 3:1。
4. 所有交互可通过键盘完成。
5. Focus Ring 使用清晰的 2px #3478F6。
6. 图表不得只依赖颜色，必须增加文字、图标、纹理或线型。
7. 图表提供数据表替代入口和可理解的屏幕阅读器摘要。
8. Toast 使用合适的 aria-live。
9. 错误信息说明问题和恢复方式。
10. 尊重 reduced motion、放大文字和高对比度设置。
11. 服务健康、数据就绪、刷新、部分失败和来源切换使用礼貌级状态播报；致命不可用使用明确警报，但不重复播报每个子错误。
12. 错误摘要先播报总体影响，再允许逐项进入失败项目；焦点不得自动跳离用户正在阅读的上一快照。
13. 来源哈希、HEAD 和错误码提供可读标签，读屏不能只读出一串无上下文字符。

## 十二、最终验收标准

- [ ] 6 个一级页面均有独立、真实的信息结构，不是只更换标题。
- [ ] 项目、角色、阶段、Bug/复测、迭代、发布、成熟度全部有明确可视化。
- [ ] 1440px 总览首屏至少呈现 4 个可视化决策模块。
- [ ] 所有说明性正文不超过两行，详情进入抽屉或 Tooltip。
- [ ] 最新 11 个角色和阶段 0–10 完整出现。
- [ ] 所有图表的数据字段、单位、来源和计算口径明确。
- [ ] 汇总数字和明细计算结果一致。
- [ ] 所有演示数据在页面级和组件级均有标识。
- [ ] 不出现虚假的“实时”“已同步”或“已发布”状态。
- [ ] Blocker 或发布门禁未通过时，发布状态明确为“阻塞”。
- [ ] 颜色不是唯一状态表达方式。
- [ ] 键盘、焦点、对比度和图表替代内容符合 WCAG 2.2 AA。
- [ ] 1440px、1024px、390px 三类尺寸均无页面级横向溢出。
- [ ] 所有组件具备加载、空、错误、过期、待接入和演示数据状态。
- [ ] 所有页面明确区分 `live-repository`、`degraded-live`、`stale-memory`、`static-fallback` 和 `not-ready`。
- [ ] 服务健康与数据就绪分别展示；进程健康不替代数据就绪。
- [ ] 每张关键卡片、图表和明细可查看 source_path、source_sha256、source_updated_at、observed_at、root_head、工作树、新鲜度与覆盖。
- [ ] 观测时间不冒充源更新时间；时间未知时明确显示未知。
- [ ] 单项目／单行损坏保留其他可用数据并列出失败范围。
- [ ] 真实 0、筛选无结果、未登记、覆盖不可用、未就绪和读取失败互不混淆。
- [ ] hash_mismatch、conflict、working-copy-modified 和观测不一致都有非颜色状态与恢复说明。
- [ ] 角色无结构化证据时不显示在线／离线；后端目录存在不等于已实现。
- [ ] 问题覆盖不可用不显示“0 个问题”；发布 URL 不等于健康或生产上线。
- [ ] Control Center 保持只读，不出现可执行审批、状态、问题、发布、Git 或文件修复入口。
- [ ] 视觉保持专业、克制、清晰，不使用无业务价值的装饰图表。
- [ ] 设计稿中不指定前端框架，不输出实现代码。
- [ ] 在超级无敌帅超超总批准设计稿前，不交给前端实现。

## 十三、审核门禁

本提示词 v1.1 必须先由超级无敌帅超超总审核。

- 超级无敌帅超超总批准提示词后，才允许生成设计稿或交互原型。
- 设计稿完成后必须再次提交超级无敌帅超超总审核。
- 超级无敌帅超超总批准设计稿后，才允许前端工程师入场实现。
- 未经批准，不得跳过任何一道门禁。
