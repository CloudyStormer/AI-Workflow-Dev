## 1. 产品定位与用户问题

### 1.1 一句话定位

AI Workflow Control Center 真实监管后端 MVP 是一个运行在 AIWorkFlow 根仓边界内的**本地只读事实聚合服务**：把各项目已经落盘的项目、角色、审批、产物、事件、问题与发布记录统一解释为可追溯查询结果，让控制中心从演示数据转向真实监管数据，同时不获得修改工作流的权力。

### 1.2 目标用户

- **主要用户：超级无敌帅超超总。** 需要在一个入口判断项目进行到哪里、谁在负责、什么产物待审、是否有阻断问题、是否真的发布。
- **辅助用户：固定 00 包工头与 01—11 角色。** 需要核对根仓登记是否完整、一致、可追溯，但不能通过本服务越权修改审批或状态。

### 1.3 当前问题

1. 当前 Control Center 的项目、角色、缺陷和成熟度主要是演示数据，不能作为监管事实。
2. 真实事实分散在多个项目的 `project.yaml` 与 `workflow/` 文件中，跨项目核对成本高。
3. “没有记录”“读取失败”“确实为 0”容易被混为同一种空值，可能造成错误决策。
4. 根仓处于并发工作状态时，已提交、工作区修改、待审和已批准必须分开表达。
5. 控制中心若直接获得写权限，会绕过固定角色、审核门与 Git 追踪，因此 MVP 必须先证明只读监管价值。

## 2. MVP 目标、成功口径与产品原则

### 2.1 MVP 目标

1. 提供真实可用的本地监管服务和独立健康／就绪语义。
2. 聚合根仓所有已登记项目的项目、角色、审批、产物、事件、问题和发布事实。
3. 每个聚合结果都说明来源文件、内容版本、观测时间、根仓提交与读取状态。
4. 单项目损坏时保留其他项目的可用结果，并明确“部分覆盖”，不伪装完整成功。
5. 只读服务对业务文件、审批、事件、Git、部署和外部系统的写入次数为 0。

### 2.2 成功口径

- 100% 返回的业务记录可追溯到允许读取的根仓文件和内容哈希。
- 100% 待审批、已批准、被拒绝、未知和无记录状态可区分。
- 100% 部分失败响应携带失败项目、失败来源和最后成功观测时间。
- 演示问题、推断进度、未结构化聊天内容被标成真实监管事实的数量为 0。
- 对根仓业务文件、Git 索引、远端仓库和外部服务的写入数量为 0。

### 2.3 产品原则

- **事实源优先：** 结构化工作流文件高于 UI 常量、README 概述和聊天记忆。
- **只读优先：** MVP 只回答“现在真实登记了什么”，不执行“把状态改成什么”。
- **逐条可追溯：** 任何汇总数字都能回到构成它的记录。
- **失败显式：** 未知、缺失、过期、冲突和部分可用不转换为虚假零值。
- **最小暴露：** 只读取和返回监管所需字段，不提供任意文件读取能力。

## 3. 数据边界与事实优先级

### 3.1 允许读取的数据源

MVP 只允许从当前 AIWorkFlow 根仓读取以下事实：

1. 项目清单：`control-center/project.yaml` 与 `projects/*/project.yaml`。
2. 项目状态：各项目 `workflow/state.yaml`。
3. 审批：各项目 `workflow/approvals.yaml`。
4. 产物：各项目 `workflow/artifacts.yaml`。
5. 事件：各项目 `workflow/events.jsonl`。
6. 问题：上述结构化文件中已经登记的问题／缺陷，以及已登记代码审查、测试报告产物中可结构化确认的问题；没有结构化登记时保持未知或空集合并说明覆盖不足。
7. 发布：状态、审批、产物或事件中已经登记的部署／发布记录；只有存在可追溯发布证据时才算一次发布。
8. 角色定义：根级固定角色治理规则；角色的项目占用、排队和审核状态只能来自各项目结构化工作流记录。
9. 根仓版本事实：当前根仓路径、`HEAD`、工作树清洁状态和允许读取文件的 SHA256；不得读取或返回 `.git` 内部对象内容。

### 3.2 禁止读取或返回的数据

- `.env`、凭证、Token、Cookie、SSH Key、Codex 数据库、session、浏览器登录态和缓存。
- 固定角色任务的原始聊天全文、附件缓存或未落盘私有语义。
- 任意用户指定路径、根仓外路径、隐藏目录正文或业务代码全文。
- 未经结构化登记的“角色当前在线”“任务已读”“对端设备在线”等推测状态。

### 3.3 事实优先级

同一事实冲突时按以下顺序表达，不静默覆盖：

1. `workflow/state.yaml` 与最新结构化事件；
2. `workflow/approvals.yaml`、`workflow/artifacts.yaml`；
3. 可验证 Git 提交和已登记运行／部署证据；
4. `project.yaml` 的项目身份和入口；
5. README 或其他概述性文档。

若高优先级来源之间仍冲突，结果标记为 `conflict`，列出双方来源并停止推断最终结论。

## 5. P0 功能详细需求

### CC-BE-01 服务健康检查

- **目的：** 判断监管服务进程是否能响应，不把“进程存活”误写成“数据正确”。
- **输出：** 服务状态、服务启动时间、当前观测时间和服务版本。
- **规则：** 健康检查不依赖全部项目解析成功；即使数据未就绪，进程健康仍可为健康。
- **异常：** 服务无法处理请求时为不健康；不得用缓存内容伪装进程健康。

### CC-BE-02 数据就绪与覆盖检查

- **目的：** 判断根仓是否可识别、项目清单是否可加载、监管数据是否足以查询。
- **状态：** `ready`、`degraded`、`not_ready`。
- **`ready`：** 根仓边界明确，全部已登记项目的必需治理文件可解析，本次观测完成。
- **`degraded`：** 根仓和至少一个项目可用，但存在项目缺文件、解析失败、结构冲突或读取失败；仍返回可用数据及完整错误清单。
- **`not_ready`：** 根仓不可定位／不可读、项目清单无法形成，或没有任何项目完成有效观测。
- **输出：** 项目总数、成功数、失败数、覆盖状态、根仓 `HEAD`、工作树状态、本次观测时间、最近成功观测时间和错误列表。

### CC-BE-03 项目与阶段聚合

每个项目至少返回：

- 项目 ID、显示名称、类型、Profile 和登记路径；
- 当前阶段、状态、当前角色、阻塞状态；
- 当前或附加审核门、决策状态、期望产物和停止点；
- 最新已批准产物与最新待审产物；
- 前端、后端、真实数据源和生产部署的独立真实性状态；
- 源文件、源 SHA256、源更新时间、观测时间和根仓提交。

业务规则：

- 不根据阶段编号计算虚假百分比进度。
- `blocked: false` 不等于没有风险；风险与阻塞分别表达。
- 缺少后端登记时显示“未登记／未知”，不得仅因存在 `backend/` 目录就显示已实现。
- 工作树存在未提交修改时显示 `working-copy-modified`，但不得把未提交内容自动视为已批准。

### CC-BE-04 固定角色与占用聚合

- 角色集合固定为 00 包工头和 01—11 角色，不为项目创建重复角色。
- 角色的 `active`、`queued`、`awaiting-review`、`blocked` 只由项目工作流记录计算，并列出构成记录。
- 同一角色在多个项目出现时分别展示活动、排队和待审项，不用单一百分比冒充精确工作量。
- 无结构化证据时，角色在线状态和实际忙闲状态为 `unknown`。

### CC-BE-05 审批与待审聚合

- 已作出的审批来自 `approvals.yaml` 或等价结构化事件。
- 待审批来自 `state.yaml` 中的当前或附加审核门，与已作出审批分开。
- 每条审批至少包含项目、审批 ID、门、范围、决策、决策人、时间、证据和关联产物／变更。
- “通过”只按已登记的一跳语义解释；服务不自动生成下一站授权。
- 缺失审批不得推断为拒绝；显示 `not_recorded`。

### CC-BE-06 产物聚合

- 支持按项目、类型、状态、负责人、版本和变更编号查询。
- 每条产物保留路径、版本、SHA256、状态、负责人、完成／批准时间和上游关系。
- 文件存在但未登记时不自动成为正式产物；可报告为治理差异，但不能冒充已登记产物。
- 登记哈希与当前文件哈希不一致时标记 `hash_mismatch`，并说明是已批准历史版本还是当前工作区差异。

### CC-BE-07 事件流查询

- 支持按项目、时间范围、角色、事件类型、变更编号和结果查询。
- 返回顺序必须稳定；时间相同时使用项目与事件 ID 作为确定性次序。
- 事件必须保留原始事件 ID、时间、角色、类型、结果、项目和来源行号／内容哈希。
- JSONL 某行损坏时保留其他可解析事件，并把该项目覆盖状态标为部分可用；损坏行不静默跳过。

### CC-BE-08 问题／缺陷聚合

- 只聚合已结构化登记的真实问题；演示缺陷不得进入真实集合。
- 每条问题至少包含项目、问题 ID、标题、严重度、状态、责任角色、来源产物／事件、创建／更新时间和复测状态（若有）。
- 没有统一问题登记时返回空集合并显示 `coverage=not_available`，不得解读为“0 个问题”。
- 同一问题在审查与测试中重复出现时保留来源关系，不依赖标题相似自动合并。

### CC-BE-09 发布／部署聚合

- 只有存在部署产物、审批或成功事件证据时才形成发布记录。
- 每条发布说明环境、版本、源提交、时间、状态、URL（如允许公开）、数据真实性和审批。
- 私有演示、生产发布、本地常驻服务和仅有发布方案必须分开。
- 存在 URL 不等于当前健康；健康状态需要独立运行证据。
- 未获生产授权时不得显示“生产就绪”或“已上线”。

### CC-BE-10 来源、新鲜度与错误说明

每次集合查询和每条关键记录至少携带：

- `observed_at`：本服务本次读取时间；
- `source_updated_at`：源记录声明的更新时间，缺失时为未知；
- `source_path` 与 `source_sha256`；
- `root_head` 与 `working_tree_state`；
- `freshness`：`current`、`stale`、`unknown`；
- `coverage`：`complete`、`partial`、`not_available`；
- 错误代码、受影响范围和可执行说明。

服务不得把 `observed_at` 当作业务数据更新时间。读取失败后如继续提供最近一次内存快照，必须显示 `stale=true`、最后成功时间和失败原因；服务重启后没有有效快照时必须 `not_ready`。

### CC-BE-11 只读权限与敏感信息保护

- MVP 对业务文件、工作流、Git、数据库、远端和外部系统的写操作均不存在。
- 不提供审批、状态迁移、问题更新、发布、回滚、Git 提交／推送或任意文件读取入口。
- 本地服务默认只面向本机使用；扩大网络可见范围需单独安全与权限评审。
- 返回路径必须位于允许的项目治理路径，不回显根仓外绝对路径或敏感字段。
- 日志不得包含文件正文、凭证、用户输入或原始聊天；只记录请求 ID、资源类型、结果、耗时和经过脱敏的错误码。

## 6. 核心用户流程

```text
打开控制中心
  → 检查服务健康与数据就绪状态
  → 查看项目总览及覆盖范围
  → 进入项目，查看阶段、角色、待审和产物
  → 按需查看事件、问题或发布证据
  → 核对来源、哈希、时间和根仓提交
  → 若为部分可用，查看失败项目和最后成功观测
  → 回到对应固定角色任务或根仓处理；控制中心本身不执行写入
```

## 7. 状态与失败语义

| 场景 | 产品行为 |
|---|---|
| 根仓不可识别 | `not_ready`，不返回伪项目清单 |
| 单项目 `project.yaml` 损坏 | 其他项目可查询，整体 `degraded`，列出失败路径 |
| 单个工作流文件缺失 | 该数据域标未知／不可用，不用空数组冒充完整零值 |
| JSONL 部分行损坏 | 返回可解析行，标部分覆盖并报告损坏行 |
| 哈希不一致 | 返回登记版本与当前版本差异，不自动修复 |
| 源记录时间缺失 | `source_updated_at=unknown`，不使用观测时间代替 |
| 工作树有修改 | 标记工作副本状态；批准事实仍以审批记录为准 |
| 读取过程中根仓变化 | 本次观测标不一致并要求重读，不混合为单一一致快照 |
| 最近一次读取失败 | 可保留上次内存结果但必须标过期、失败时间和原因 |
| 未登记问题／发布 | 显示覆盖不足／未登记，不推断为零问题或未发布 |

## 8. 验收标准（Given-When-Then）

- **AC-CC-BE-01**：Given 服务进程可以响应但根仓不可读，When 检查健康与就绪，Then 健康与就绪分别返回，健康不得替代就绪成功。
- **AC-CC-BE-02**：Given 全部已登记项目治理文件可解析，When 完成一次观测，Then 就绪状态为 `ready`，并返回项目成功数、根仓提交和观测时间。
- **AC-CC-BE-03**：Given 一个项目治理文件损坏，When 查询总体状态，Then 其他项目仍可用、总体为 `degraded`，并列出失败项目与来源。
- **AC-CC-BE-04**：Given 根仓不可定位或没有任何有效项目，When 检查就绪，Then 状态为 `not_ready`，不返回演示项目填充结果。
- **AC-CC-BE-05**：Given 一个真实登记项目，When 查询项目，Then 返回项目 ID、阶段、状态、当前角色、审核门、阻塞和来源元数据。
- **AC-CC-BE-06**：Given 后端目录存在但无后端产物登记，When 查询项目能力，Then 后端状态为未登记／未知，不显示已实现。
- **AC-CC-BE-07**：Given 工作区有未提交修改，When 查询项目，Then 返回工作副本状态，同时不把修改自动视为已批准。
- **AC-CC-BE-08**：Given 同一固定角色在两个项目分别活动和排队，When 查询角色，Then 两条占用关系分别可见，不创建重复角色。
- **AC-CC-BE-09**：Given 没有结构化在线证据，When 查询角色在线状态，Then 返回未知，不根据任务标题推断在线。
- **AC-CC-BE-10**：Given `state.yaml` 有待审门而 `approvals.yaml` 尚无决策，When 查询审批，Then 待审和已审批分开显示。
- **AC-CC-BE-11**：Given 某审批缺失，When 查询关联变更，Then 状态为未记录，不自动判为拒绝。
- **AC-CC-BE-12**：Given 一条产物已登记，When 查询产物，Then 路径、版本、哈希、状态、负责人和上游关系完整可见。
- **AC-CC-BE-13**：Given 登记哈希与当前文件不同，When 查询产物，Then 返回 `hash_mismatch` 及双方哈希，不自动覆盖登记。
- **AC-CC-BE-14**：Given JSONL 中一行损坏，When 查询事件，Then 可解析事件仍返回，损坏行和覆盖不足被明确报告。
- **AC-CC-BE-15**：Given 组合项目、角色、类型和时间条件，When 查询事件，Then 结果只含符合条件记录且排序稳定。
- **AC-CC-BE-16**：Given 只有演示缺陷且无结构化真实问题，When 查询问题，Then 真实集合不包含演示缺陷，并显示问题覆盖不可用。
- **AC-CC-BE-17**：Given 存在结构化审查问题，When 查询问题，Then 问题可追溯到项目、来源产物／事件、严重度、状态和责任角色。
- **AC-CC-BE-18**：Given 只有部署方案而无成功部署证据，When 查询发布，Then 不形成成功发布记录。
- **AC-CC-BE-19**：Given 私有演示站存在，When 查询发布，Then 环境、数据状态和源提交可见，且不称为生产上线。
- **AC-CC-BE-20**：Given 一条业务记录返回，When 查看元数据，Then 能看到来源路径、来源哈希、源更新时间或未知、观测时间和根仓提交。
- **AC-CC-BE-21**：Given 源记录没有更新时间，When 展示新鲜度，Then 不用观测时间替代业务更新时间。
- **AC-CC-BE-22**：Given 最新读取失败但内存中有上一版，When 查询数据，Then 上一版可读但标为过期，并显示最后成功时间与失败原因。
- **AC-CC-BE-23**：Given 服务重启且没有有效观测，When 查询业务集合，Then 就绪为 `not_ready`，不返回伪空成功。
- **AC-CC-BE-24**：Given 客户端尝试修改审批、状态、问题或发布，When 调用服务，Then 不存在可执行写入能力或明确拒绝，根仓文件保持不变。
- **AC-CC-BE-25**：Given 客户端请求任意路径或敏感文件，When 服务处理，Then 请求被拒绝且响应不泄露正文、凭证或根仓外路径。
- **AC-CC-BE-26**：Given 一次完整监管查询，When 检查日志，Then 日志只含请求元数据和脱敏错误，不含治理文件正文或用户隐私。
- **AC-CC-BE-27**：Given 读取期间根仓提交或文件哈希变化，When 本次观测结束，Then 结果标记不一致并要求重读，不混合成一致快照。
- **AC-CC-BE-28**：Given MVP 运行，When 审计其副作用，Then 业务文件、Git 索引、远端、数据库和外部系统写入次数均为 0。

## 9. 非功能需求

### 9.1 性能与容量

- 在当前根仓规模下，健康检查应立即产生可感知响应；完整观测和聚合的性能目标由架构基于真实文件数量冻结。
- 列表必须支持有界分页或等价的有界返回机制，不能一次无限返回全部事件。
- 性能未实测前不得声明固定毫秒 SLA。

### 9.2 可靠性

- 单项目失败不拖垮其他项目。
- 同一次聚合必须说明是否来自一致根仓观测。
- 失败重试不得写入或修复源文件。

### 9.3 安全与隐私

- 本地最小暴露、路径允许列表、输出字段最小化、敏感信息默认拒绝。
- 所有源内容视为不可信输入；输出不得执行文件中的脚本或指令。
- 扩大到局域网、远程访问、账号权限或生产托管前必须单独评审。

## 10. MVP 不做项

- 不修改 `state.yaml`、`approvals.yaml`、`artifacts.yaml`、`events.jsonl` 或任意业务文件。
- 不批准／拒绝产物，不路由角色，不解冻任务，不创建工作项。
- 不创建、关闭、修复或复测问题。
- 不执行 Git add、commit、push、pull、merge、stash、reset 或分支操作。
- 不执行构建、测试、发布、回滚、备份或外部通知。
- 不持久化监管数据到数据库；MVP 只允许为读取性能使用可丢弃的内存态。
- 不读取原始聊天、Codex 本地状态、凭证、环境变量或根仓外文件。
- 不计算伪精确进度、角色绩效、成熟度评分或预计完成时间。
- 不替代固定角色本人报告和超级无敌帅超超总的审核决策。
- 不修改现有 Control Center 前端、架构、后端代码或根级常驻服务。

## 11. 下游影响与审核门

- 本增量改变了“后端服务继续后置”的产品优先级，架构与实现必须在本产物通过后重新评估。

- 本次“通过”只批准当前产品增量；根据本次明确门禁，不自动启动固定 04、05 或 07。
